# Тема 9. Память, GC и ссылки

> Читаешь теорию → решаешь 20 задач в `Tasks.java` → гоняешь тесты:
> `./gradlew test --tests "handbook.java.memory.*"`. Застрял — сверься с
> [`solutions/Solutions.java`](solutions/Solutions.java).

Про то, как JVM управляет памятью и почему Android-приложения текут. Разбираем: куча/стек и
достижимость, сборщик мусора, четыре силы ссылок (strong/soft/weak/phantom), `WeakHashMap`,
`ReferenceQueue`, и — главное для Android — **паттерны утечек и их лечение**.

---

## 1. Стек, куча и достижимость

- **Стек** — у каждого потока свой: локальные переменные и ссылки, кадры вызовов. Освобождается сам
  при выходе из метода.
- **Куча (heap)** — все объекты. Ими управляет **сборщик мусора (GC)**.

Объект жив, пока **достижим** — есть цепочка ссылок от **GC-root**. Корни: локальные переменные живых
потоков, **статические поля**, активные потоки, JNI-ссылки. Нет пути от корня → объект — мусор.

```java
Object obj = new Object();      // достижим (локальная переменная — root)
WeakReference<Object> w = new WeakReference<>(obj);
obj = null;                     // недостижим → может быть собран
```

## 2. Как работает GC

GC находит достижимые объекты (mark) и освобождает остальные (sweep/compact). JVM использует
**поколенческую** сборку: большинство объектов умирают молодыми, поэтому куча делится на **young**
(частые дешёвые сборки) и **old** (редкие). Пережившие несколько сборок «переезжают» в old.

Важно: **GC недетерминирован**. Ты не управляешь моментом сборки; `System.gc()` — лишь *просьба*.
Нельзя полагаться на своевременность GC для освобождения ресурсов (файлов, сокетов) — для них есть
try-with-resources (тема 5).

## 3. Четыре силы ссылок

| Ссылка | Когда собирается объект | Применение |
|--------|-------------------------|------------|
| **Strong** (обычная) | пока достижим — НЕ собирается | по умолчанию |
| **`SoftReference`** | только при НЕХВАТКЕ памяти | память-чувствительный кэш |
| **`WeakReference`** | при следующей сборке, если нет strong | кэши/слушатели без удержания |
| **`PhantomReference`** | уже собран; ставится в очередь ПОСЛЕ | пост-мортем очистка ресурсов |

```java
WeakReference<Bitmap> w = new WeakReference<>(bitmap);
w.get();      // Bitmap или null, если уже собран
w.clear();    // явно оборвать (после этого get() == null)
```

`SoftReference` держит объект, пока памяти достаточно, — хороша для кэшей, которые «не жалко» сбросить
под давлением. `WeakReference` не мешает сборке вообще — ей держат ссылки, которые не должны продлевать
жизнь объекту (например, слушатель на `Activity`).

## 4. `ReferenceQueue` и `PhantomReference`

Слабую/фантомную ссылку можно связать с **`ReferenceQueue`**: когда объект собран, ссылка **попадает в
очередь** — сигнал «пора зачистить сопутствующее». `WeakHashMap` так удаляет протухшие записи; на этом же
построен `PhantomReference` для безопасного освобождения нативных ресурсов (замена ненадёжному
`finalize`).

```java
ReferenceQueue<Object> q = new ReferenceQueue<>();
WeakReference<Object> w = new WeakReference<>(obj, q);
// ... после сборки obj: q.poll() вернёт w
```

## 5. `WeakHashMap`

Мапа, чьи **ключи держатся слабо**: как только на ключ не осталось сильных ссылок, запись
автоматически исчезает. Годится для метаданных, привязанных к объекту, которые не должны продлевать его
жизнь. (Значения при этом — strong; следи, чтобы значение не ссылалось обратно на ключ.)

## 6. Утечки памяти в Android

«Утечка» на JVM — не потерянный указатель, а **объект, который остаётся достижим, хотя уже не нужен**.
В Android чаще всего утекает `Activity`/`Context` (мегабайты View, Bitmap), потому что на неё держит
ссылку что-то долгоживущее. Типичные причины:

- **Нестатический внутренний / анонимный класс.** Он хранит НЕЯВНУЮ ссылку на хозяина (синтетическое
  поле `this$0`). Если такой объект переживает `Activity` — та не собирается.

  ```java
  // ❌ анонимный Runnable держит ссылку на Activity; отложенное сообщение переживает экран
  handler.postDelayed(() -> updateUi(), 60_000);
  ```

  > Нюанс: `this$0` создаётся, только когда внутренний класс реально ОБРАЩАЕТСЯ к хозяину (полю/методу).
  > На практике колбэки почти всегда обращаются — потому и текут.

- **Статическое поле**, ссылающееся на `Context`/`View` — статик это GC-root, живёт всё время процесса.
- **Долгоживущий синглтон/коллекция слушателей**, куда подписались и забыли отписаться.
- **`Handler`** с отложенным сообщением, **`ThreadLocal`** без `remove()` в пуле потоков, фоновый поток,
  держащий `Activity`.

### Лечение

- Внутренние классы, живущие дольше хозяина, делай **`static`** и держи `Context`/`Activity` через
  **`WeakReference`**.
- **Снимай** колбэки/слушатели в `onDestroy` (`handler.removeCallbacks`, отписка).
- Не клади `Context` в статические поля; чисти `ThreadLocal.remove()`.
- Инструменты: **LeakCanary** — автоматически ловит недоубитые `Activity` (внутри — слабая ссылка +
  форс GC + проверка, собралась ли; ровно как в задаче СЛ20).

## 7. `finalize()` — не использовать

`Object.finalize()` **устарел** (deprecated): вызывается недетерминированно (или никогда), тормозит GC,
опасен. Для освобождения ресурсов — **`AutoCloseable` + try-with-resources** (детерминированно), а для
нативных ресурсов — `java.lang.ref.Cleaner`/`PhantomReference`.

> **Контекст Kotlin.** Ссылки и GC — общие для JVM: `WeakReference` работает так же. Kotlin не меняет
> модель памяти. Утечки через лямбды/анонимные объекты, захватывающие `this`, — та же проблема, что и в
> Java; те же лечения (слабые ссылки, отписка в `onDestroy`, `viewLifecycleOwner` и корутинные скоупы,
> привязанные к жизненному циклу).
