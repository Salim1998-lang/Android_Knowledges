Низкий уровень многопоточности: потоки, гонки, `synchronized`, `volatile`, **модель памяти Java (JMM)
и happens-before**, атомики/CAS, `wait`/`notify`, дедлоки, `ThreadLocal`, прерывание. В Android поверх
этого лежат корутины/`Handler`, но понимать фундамент обязательно.

## 1. Потоки: `Thread` и `Runnable`

Поток — независимая линия исполнения. Задаётся `Runnable` (что делать), запускается `Thread`:

```java
Thread t = new Thread(() -> doWork());
t.start();     // запускает НОВЫЙ поток (НЕ run() — тот выполнил бы в текущем!)
t.join();      // ждём завершения t
```

`start()` vs `run()`: `run()` — обычный вызов в текущем потоке; `start()` создаёт новый поток. Результат
из потока забирают через общий изменяемый объект (массив/атомик) после `join()`.

## 2. Гонки (race conditions)

Когда несколько потоков **читают-изменяют-пишут** общие данные без синхронизации, обновления теряются:

```java
count++;   // НЕ атомарно: read count → +1 → write. Два потока могут прочитать одно и то же.
```

10 000 инкрементов из двух потоков дадут не 20 000, а меньше — часть потерялась. Лечится
синхронизацией, атомиками или неизменяемостью.

## 3. `synchronized` — интринсик-лок (монитор)

У каждого объекта есть монитор. `synchronized` даёт **взаимное исключение** (только один поток в
секции) И **видимость** (изменения видны после выхода из секции):

```java
synchronized (lock) { count++; }        // блок на конкретном объекте
public synchronized void inc() { ... }  // метод: лок на this
```

Интринсик-локи **реентерабельны**: поток, уже держащий монитор, может войти в него снова. Держи
секцию как можно короче.

## 4. `volatile` и модель памяти (JMM)

Без синхронизации нет гарантии, что запись одного потока **увидит** другой: у потоков могут быть кэши,
а компилятор/процессор вправе переупорядочивать инструкции. **JMM** описывает, когда запись
гарантированно видна — через отношение **happens-before**: если A happens-before B, то эффекты A видны в B.

Что создаёт happens-before:
- освобождение монитора happens-before его последующего захвата (`synchronized`);
- запись в `volatile`-поле happens-before последующего чтения этого поля;
- `Thread.start()` happens-before кода потока; код потока happens-before `join()`;
- инициализация `final`-полей happens-before публикации объекта.

**`volatile`** даёт **видимость** (и запрет переупорядочивания вокруг обращения), но **НЕ атомарность**
составных операций:

```java
volatile boolean running = true;   // ✅ флаг остановки: смену увидят все потоки
volatile int count;
count++;                           // ❌ всё равно гонка — это read-modify-write, а не одна операция
```

Классический паттерн — **флаг остановки** (`while (running) {...}`) и **безопасная публикация**: записать
данные в обычные поля, затем выставить `volatile`-флаг; читатель, увидев флаг, гарантированно видит и
данные.

## 5. Атомики и CAS

`java.util.concurrent.atomic.*` дают атомарные операции **без блокировок**, поверх аппаратного
**CAS (compare-and-swap)**:

```java
AtomicInteger c = new AtomicInteger();
c.incrementAndGet();          // атомарный ++c
c.getAndIncrement();          // выдача уникальных id
c.addAndGet(5);
c.compareAndSet(expect, upd); // «если ещё expect — поставь upd», иначе false
c.updateAndGet(x -> x * 2);   // атомарная функция (внутри — CAS-цикл с повтором)
```

**CAS-цикл** — основа lock-free алгоритмов: прочитать текущее, вычислить новое, попробовать
`compareAndSet`; при неудаче (кто-то опередил) — повторить. Так делают атомарный максимум, стек
Трайбера, спин-лок. `AtomicReference` то же для ссылок (например, публикация неизменяемой копии).

## 6. `wait` / `notify` — координация по условию

Иногда поток должен **ждать условия** (буфер не пуст/не полон). `wait`/`notify` работают ТОЛЬКО внутри
`synchronized` на том же мониторе:

```java
public synchronized E take() throws InterruptedException {
    while (queue.isEmpty()) wait();   // отпускает монитор и спит, пока не разбудят
    E e = queue.remove();
    notifyAll();                      // будит ожидающих (например, producer'ов)
    return e;
}
```

Правила: **всегда `wait` в цикле `while (условие)`** (защита от «ложных пробуждений» и от того, что
условие изменилось), предпочитай `notifyAll` вместо `notify`. Это фундамент producer-consumer.

## 7. Дедлоки

**Дедлок** — потоки навсегда ждут друг друга. Классика — два лока, захваченные в разном порядке:

```
Поток1: lock(A) … lock(B)
Поток2: lock(B) … lock(A)   // взаимная блокировка
```

Главная защита — **единый порядок захвата** локов (например, по `id`):

```java
Account first  = from.id <= to.id ? from : to;
Account second = from.id <= to.id ? to : from;
synchronized (first) { synchronized (second) { /* перевод */ } }
```

Ещё помогают: сокращать вложенность локов, `tryLock` с таймаутом (тема 8), неизменяемость.

## 8. `ThreadLocal` — thread-confinement

`ThreadLocal<T>` даёт КАЖДОМУ потоку свой экземпляр значения — переменная перестаёт быть общей, гонок
нет по определению:

```java
ThreadLocal<SimpleDateFormat> fmt = ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy"));
fmt.get().format(date);   // у каждого потока — свой (не thread-safe) форматтер, без синхронизации
```

⚠️ **В Android** держи `ThreadLocal` осторожно: значение живёт, пока жив поток (в пулах потоки
переиспользуются) — незачищенный `ThreadLocal` с ссылкой на `Context`/`Activity` = **утечка**. Чисти
`remove()`, когда закончил.

## 9. Прерывание (interruption)

Кооперативная отмена потока: `t.interrupt()` ставит флаг; блокирующие методы (`sleep`, `wait`, `join`)
бросают `InterruptedException`:

```java
try { Thread.sleep(10_000); }
catch (InterruptedException e) { /* прервали — сворачиваемся */ }
```

Нельзя «убить» поток силой — только попросить. Пойманное `InterruptedException` обычно либо
пробрасывают, либо восстанавливают флаг: `Thread.currentThread().interrupt()`.

> **Контекст Android/Kotlin.** Прямая работа с `Thread`/`synchronized` в приложениях вытеснена
> корутинами (structured concurrency, отмена через `CoroutineScope`). Но `@Volatile`, атомики,
> `synchronized` в Kotlin — те же, а JMM/happens-before — общий фундамент JVM. Библиотеки и SDK по-прежнему
> полны низкоуровневой синхронизации.
