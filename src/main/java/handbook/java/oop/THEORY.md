## 1. Инкапсуляция

Поля — `private`, доступ — через методы. Это не бюрократия: снаружи не видно, как хранится
состояние, и его нельзя привести в некорректное состояние в обход инвариантов.

```java
public final class BankAccount {
    private int balance;                       // никто снаружи не трогает напрямую
    public BankAccount(int initial) { this.balance = initial; }
    public int balance() { return balance; }
    public void deposit(int amount) { balance += amount; }  // единственная точка изменения
}
```

## 2. Интерфейсы, `default`- и `static`-методы

Интерфейс — контракт: «что умеет», без «как». Программируй **на интерфейс**, а не на конкретный
класс — так реализацию можно подменить:

```java
void printName(Named n) { ... }   // примет ЛЮБУЮ реализацию Named
```

С Java 8 у интерфейса могут быть **тела** методов:

- `default`-метод — реализация по умолчанию, наследуется реализующими классами (можно
  переопределить). Так в API добавляют методы, не ломая существующие реализации.
- `static`-метод — утилита, привязанная к интерфейсу (`Comparator.naturalOrder()`).
- `private`-метод (Java 9+) — вспомогательный, для переиспользования внутри `default`-методов.

```java
interface Greeter {
    String subject();                                   // абстрактный
    default String greet() { return "Hello, " + subject() + "!"; }   // с телом
}
```

**Функциональный интерфейс** — ровно один абстрактный метод (`default`/`static` не считаются).
Такой можно реализовать лямбдой: `Greeter g = () -> "World";`.

## 3. Абстрактные классы vs интерфейсы

| | Интерфейс | Абстрактный класс |
|---|-----------|-------------------|
| Множественность | класс реализует **много** интерфейсов | наследует **один** класс |
| Состояние (поля) | только константы | обычные поля есть |
| Конструктор | нет | есть |
| Когда | контракт/способность (`Comparable`, `Runnable`) | общий код + состояние для семейства классов |

Абстрактный класс задаёт **шаблон** (общий код) и оставляет «дырки» — абстрактные методы:

```java
abstract class Animal {
    final String name;
    Animal(String name) { this.name = name; }
    abstract String sound();                         // дырка — заполняет подкласс
    String describe() { return name + " says " + sound(); }  // общий код
}
class Dog extends Animal {
    Dog(String name) { super(name); }               // super() вызывает конструктор базового
    String sound() { return "woof"; }
}
```

**Ромбовидный конфликт `default`-методов.** Если класс реализует два интерфейса с одинаковым
`default`-методом — компилятор **заставит** разрешить конфликт вручную:

```java
interface Walker  { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }
class Amphibian implements Walker, Swimmer {
    public String move() { return Walker.super.move() + "/" + Swimmer.super.move(); }
}
```

## 4. Наследование против композиции

**Наследование** — «IS-A» (собака — это животное). Сильная связь: подкласс зависит от внутренностей
базового, легко нарушить инварианты. Классический совет — **«предпочитай композицию наследованию»**.

**Композиция** — «HAS-A» (у машины ЕСТЬ двигатель). Объект держит другой объект и делегирует ему:

```java
class Car {
    private final Engine engine;              // HAS-A
    Car(Engine engine) { this.engine = engine; }
    int power() { return engine.power(); }    // делегирование
}
```

Плюсы композиции: слабая связанность, можно подменять зависимость (в т.ч. в тестах), нет хрупкости
иерархий. Наследование оставляй для настоящих «IS-A» и шаблонных методов.

## 5. Шаблонный метод и `final`

`final`-метод нельзя переопределить. Это основа паттерна **шаблонный метод**: базовый класс
фиксирует скелет алгоритма (`final`), а шаги отдаёт подклассам:

```java
abstract class Report {
    abstract String body();                       // шаг подкласса
    final String render() { return "[" + body() + "]"; }  // скелет, менять нельзя
}
```

`final` бывает у: переменной (нельзя переприсвоить), метода (нельзя переопределить), класса (нельзя
наследовать — `String`, обёртки).

## 6. `static` против `instance`

- **instance-член** — свой у каждого объекта.
- **static-член** — один на весь класс, общий для всех объектов, живёт даже без единого экземпляра.

```java
class Widget {
    private static int count = 0;    // общий счётчик
    private final int id;            // свой у каждого
    Widget() { id = ++count; }       // каждый новый объект двигает общий count
}
```

`static`-методы не имеют `this`, вызываются от класса (`Widget.count()`). Важно: `static`-методы
**не переопределяются**, а **скрываются** — вызов резолвится по типу ссылки на этапе компиляции, а не
по фактическому объекту (в отличие от обычных методов — там динамический полиморфизм).

## 7. Порядок инициализации

При первом обращении к классу он **загружается**: один раз выполняются `static`-поля и `static`-блоки
(сверху вниз). Затем при **каждом** `new`: instance-поля и instance-блоки → тело конструктора
(предварительно — конструктор базового класса через `super()`).

```
static-блок      // однажды, при загрузке класса
--- на каждый new: ---
super(...)        // сначала базовый
instance-блок
конструктор
```

## 8. `enum` — это класс

`enum` — не просто список констант, а полноценный класс с фиксированным набором экземпляров. У него
могут быть поля, конструктор, методы:

```java
enum Coin {
    PENNY(1), NICKEL(5), DIME(10);
    private final int cents;
    Coin(int cents) { this.cents = cents; }   // конструктор зовётся для каждой константы
    int cents() { return cents; }
}
```

**Поведение на константу** — каждая константа может переопределять абстрактный метод:

```java
enum Operation {
    PLUS  { public int apply(int a, int b) { return a + b; } },
    MINUS { public int apply(int a, int b) { return a - b; } };
    public abstract int apply(int a, int b);
}
```

Полезное: `values()` (все константы), `valueOf("DIME")` (по имени), `ordinal()`, `name()`. Enum —
**лучший способ синглтона**: единственный `INSTANCE` создаётся лениво и потокобезопасно, устойчив к
рефлексии и сериализации:

```java
enum Registry { INSTANCE; private final Map<String,Integer> data = new HashMap<>(); }
```

## 9. Вложенные классы — и утечки в Android

Четыре вида:

| Вид | Объявление | Держит ссылку на внешний объект? |
|-----|-----------|----------------------------------|
| **Static nested** | `static class Inner` | **нет** |
| **Inner (внутренний)** | `class Inner` (без `static`) | **да, неявно** |
| **Local** | класс внутри метода | да + захват локальных |
| **Anonymous** | `new Runnable() { ... }` | да + захват локальных |

Static nested — просто класс «в неймспейсе» внешнего, отдельный. Хорош для builder'ов:

```java
User u = User.builder().name("Ann").age(30).build();   // Builder — static nested
```

**Inner / anonymous / local** держат **неявную ссылку на внешний объект** и видят его поля:

```java
class Counter {
    private int n;
    class Tick { void bump() { n++; } }   // Tick.this видит Counter.this.n
}
```

Захватываемые локальные переменные должны быть **effectively final** (не меняться после
присваивания) — поэтому лямбда/анонимный класс «замыкает» их значение:

```java
IntOp makeAdder(int base) { return x -> x + base; }   // захват base
```

⚠️ **Ловушка Android.** Нестатический внутренний/анонимный класс держит ссылку на внешний объект. Если
такой объект **переживает** внешний (например, `Handler`, `Runnable`, слушатель или
`AsyncTask`, отправленный в очередь/поток), он **не даёт `Activity` собраться сборщиком мусора** —
утечка памяти. Лечится: делать такие классы `static` + держать `WeakReference` на `Activity`/`Context`,
либо снимать колбэки в `onDestroy`. Подробнее про ссылки и утечки — в теме «Память, GC и ссылки».
