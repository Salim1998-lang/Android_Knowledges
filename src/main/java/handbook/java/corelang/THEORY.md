## 1. Примитивы и обёртки

В Java восемь **примитивных** типов — они не объекты, лежат прямо в стеке/поле, не могут быть
`null`:

| Тип | Размер | Диапазон / примечание |
|-----|--------|-----------------------|
| `boolean` | — | `true` / `false` |
| `byte` | 8 бит | −128..127 |
| `short` | 16 бит | −32 768..32 767 |
| `char` | 16 бит | 0..65 535 (код UTF-16) |
| `int` | 32 бита | ±2.1 млрд |
| `long` | 64 бита | ±9.2·10¹⁸ (литерал с суффиксом `L`: `10L`) |
| `float` | 32 бита | суффикс `f`: `1.5f` |
| `double` | 64 бита | тип по умолчанию для дробных |

У каждого примитива есть **обёртка** (wrapper) — настоящий объект-класс: `Integer`, `Long`,
`Boolean`, `Character`, `Double` и т.д. Обёртка **может быть `null`** и хранится в куче. Коллекции
(`List<Integer>`) умеют держать только объекты — поэтому примитивы в них живут как обёртки.

```java
int a = 5;               // примитив, в стеке
Integer b = 5;           // обёртка, в куче (+ автоупаковка, см. ниже)
Integer c = null;        // так можно — обёртка nullable
// int d = null;         // ОШИБКА компиляции — примитив не бывает null
```

> В Kotlin этого деления в коде не видно: `Int` компилируется то в примитив `int`, то в обёртку
> `Integer` в зависимости от контекста (nullable `Int?`, дженерики → обёртка). В Java ты выбираешь
> руками.

## 2. Автоупаковка (autoboxing) и кэш `Integer`

**Autoboxing** — автоматическое `int → Integer`, **unboxing** — `Integer → int`:

```java
Integer x = 42;          // autoboxing: компилятор вставит Integer.valueOf(42)
int y = x;               // unboxing: компилятор вставит x.intValue()
```

Две ловушки, обе спрашивают на собесах.

**Ловушка 1 — `NullPointerException` при распаковке.** Если обёртка `null`, unboxing падает:

```java
Integer n = null;
int m = n;               // NPE! под капотом n.intValue() на null
```

**Ловушка 2 — кэш `Integer` и `==`.** `Integer.valueOf` кэширует объекты для значений
**−128..127** (по спецификации). Поэтому одинаковые «маленькие» `Integer` — это **один и тот же
объект**, а «большие» — разные:

```java
Integer a1 = 100, a2 = 100;
System.out.println(a1 == a2);   // true  — оба из кэша, одна ссылка
Integer b1 = 1000, b2 = 1000;
System.out.println(b1 == b2);   // false — разные объекты!
System.out.println(b1.equals(b2)); // true — по значению
```

Мораль: **обёртки всегда сравнивай через `equals`**, `==` на них сравнивает ссылки и «случайно
работает» только в диапазоне кэша. `Long`, `Short`, `Byte`, `Character` кэшируют аналогично.

## 3. Переполнение `int`

`int` — 32-битное **знаковое** число по модулю 2³². Арифметика **молча заворачивается** (wrap
around), исключения нет:

```java
int max = Integer.MAX_VALUE;    //  2_147_483_647
System.out.println(max + 1);    // -2_147_483_648  (Integer.MIN_VALUE)!
```

Классический баг — переполнение в промежуточном вычислении. Например, среднее двух больших `int`:

```java
int mid = (low + high) / 2;     // low+high может переполниться → отрицательный mid
int mid = low + (high - low) / 2;   // безопасно
```

Как защищаться:
- считать в `long`, если сумма может вылезти за `int`: `(long) a + b`;
- либо `Math.addExact(a, b)` / `multiplyExact` — они **бросают** `ArithmeticException` при
  переполнении вместо тихого заворота.

## 4. `String`: неизменяемость и пул

`String` в Java **неизменяемый** (immutable): любой «изменяющий» метод возвращает **новый** объект,
исходный не трогается.

```java
String s = "hi";
s.concat("!");           // вернул "hi!", но результат не присвоен
System.out.println(s);   // "hi" — s не изменилась
s = s.concat("!");       // вот теперь s указывает на новый объект "hi!"
```

**Пул строк (string pool).** Строковые **литералы** интернируются: одинаковые литералы — один
объект в пуле. А `new String(...)` всегда создаёт новый объект в куче:

```java
String p = "abc";
String q = "abc";
System.out.println(p == q);            // true  — оба из пула
String r = new String("abc");
System.out.println(p == r);            // false — r отдельный объект
System.out.println(p == r.intern());   // true  — intern() возвращает объект из пула
```

Отсюда правило: **строки сравнивай через `equals`**, а не `==`. `==` сравнивает ссылки и
«срабатывает» лишь из-за пула — на данных из сети/БД (не литералах) сломается.

**Построение строк — `StringBuilder`.** Конкатенация `+` в цикле создаёт новый `String` на каждой
итерации (O(n²) по мусору). Для сборки строки в цикле — `StringBuilder` (изменяемый, O(n)):

```java
StringBuilder sb = new StringBuilder();
for (String part : parts) sb.append(part);
String result = sb.toString();
```

> `StringBuilder` не потокобезопасен (и это нормально для локальной переменной). Его синхронный
> брат `StringBuffer` android-разработчику обычно не нужен.

## 5. `==` против `equals`

- `==` для **примитивов** сравнивает значения.
- `==` для **объектов** (включая `String` и обёртки) сравнивает **ссылки** — «это один и тот же
  объект в памяти?».
- `equals` сравнивает **по содержимому** — если класс переопределил `equals` (у `String`, обёрток —
  да; подробно про контракт `equals`/`hashCode` — в теме про коллекции).

Null-безопасно сравнивать удобно через `java.util.Objects`:

```java
Objects.equals(a, b);    // не бросит NPE, даже если a == null
```

Массивы **не** переопределяют `equals` — `arr1.equals(arr2)` это ссылочное сравнение. Для сравнения
по содержимому — `Arrays.equals(arr1, arr2)`.

## 6. `char` — это число

`char` — 16-битный **беззнаковый** код UTF-16, и с ним можно делать арифметику:

```java
char c = '7';
int digit = c - '0';         // 7  — коды идут подряд '0'..'9'
char next = (char) (c + 1);  // '8'
```

Полезно для парсинга цифр и работы с символами. Проверки — `Character.isDigit(c)`,
`Character.isLetterOrDigit(c)`, `Character.toLowerCase(c)`.

## 7. Дробные числа: не сравнивай через `==`

`double`/`float` хранят приближения в двоичной форме — точного `0.1` не существует:

```java
System.out.println(0.1 + 0.2);          // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3);   // false!
```

Сравнивай с допуском (эпсилон): `Math.abs(a - b) < 1e-9`. Для денег — не `double`, а `BigDecimal`
или целые копейки (это уже тема систем-дизайна).

## 8. Аргументы передаются «по значению»

В Java **всё** передаётся по значению. Для объектов «значение» — это **копия ссылки**. Поэтому:

- через ссылку можно **менять сам объект**, и вызывающий увидит изменения;
- но **переприсвоить** параметр внутри метода — вызывающего не затронет (у него своя копия ссылки).

```java
static void mutate(int[] arr) { arr[0] = 99; }   // видно снаружи — меняем объект
static void reassign(int[] arr) { arr = new int[]{1}; } // НЕ видно — переприсвоили копию ссылки

int[] a = {0};
mutate(a);     // a[0] == 99
reassign(a);   // a[0] всё ещё 99 — reassign ничего не изменил у вызывающего
```

Примитивы копируются целиком — метод их менять «наружу» не может в принципе.
