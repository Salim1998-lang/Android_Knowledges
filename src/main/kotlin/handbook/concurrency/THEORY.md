# Тема 9. Разделяемое изменяемое состояние (Mutex)

## 1. Проблема: гонка за общим состоянием

Корутины часто работают **параллельно** (на `Dispatchers.Default` — реально на разных потоках).
Если несколько корутин меняют **одну и ту же изменяемую переменную**, возникает **гонка данных**
(data race): результат зависит от того, кто когда успел.

```kotlin
var counter = 0
withContext(Dispatchers.Default) {
    coroutineScope {
        repeat(1000) { launch { counter++ } }   // 1000 корутин, общий counter
    }
}
println(counter)   // НЕ обязательно 1000! Часто меньше.
```

Почему `counter++` ломается: это не одна операция, а три — **прочитать → прибавить → записать**
(read-modify-write). Две корутины могут прочитать одно и то же значение и обе записать `+1` — одно
приращение потеряется.

> 🧠 **Правило.** Любая операция «прочитать-изменить-записать» над общим состоянием, выполняемая
> конкурентно, должна быть **атомарной** — иначе часть изменений теряется.

## 2. Пять способов защиты

Ниже — арсенал. Идём от простого частного случая к общему.

| Способ | Когда | Идея |
|--------|-------|------|
| **Атомики** (`AtomicInteger`) | счётчики, флаги, ссылки | железо/JDK гарантируют атомарность отдельной операции |
| **Тонкое замыкание** (fine-grained confinement) | точечные обновления | каждую мутацию гнать на **один** поток |
| **Грубое замыкание** (coarse-grained) | большой блок работы с состоянием | весь блок выполнять на одном потоке |
| **`Mutex`** | произвольная критическая секция | взаимное исключение: одномоментно внутри — одна корутина |
| **Actor** | состояние + поток команд | один владелец состояния, общение через канал |

## 3. Атомики

`java.util.concurrent.atomic.*` — потокобезопасные обёртки. Отдельная операция неделима:

```kotlin
val counter = AtomicInteger(0)
counter.incrementAndGet()          // атомарный ++
counter.addAndGet(5)               // атомарный +=
counter.compareAndSet(0, 42)       // CAS: если сейчас 0 — стало 42, вернёт true
```

**CAS (compare-and-set)** — фундамент неблокирующих алгоритмов: «поменяй, только если значение всё
ещё такое, как я думал». Если не совпало — повторяем в цикле:

```kotlin
// атомарно обновить до максимума
while (true) {
    val cur = counter.get()
    if (candidate <= cur) break
    if (counter.compareAndSet(cur, candidate)) break   // удалось — выходим
}                                                       // не удалось — кто-то опередил, повтор
```

Плюс: без блокировок, быстро. Минус: защищает **одну** переменную, не составную инвариантность
(«перевести деньги с A на B» — это два поля, атомиком не покрыть).

## 4. Замыкание на поток (thread confinement)

Данные, к которым обращаются **только с одного потока**, не нуждаются в блокировках — гонок нет по
построению. В корутинах поток задаёт диспетчер.

**Тонкое (fine-grained)** — на один поток гоним **каждую мутацию**:

```kotlin
val counterCtx = Executors.newSingleThreadExecutor().asCoroutineDispatcher()
var counter = 0
withContext(Dispatchers.Default) {
    coroutineScope {
        repeat(1000) { launch { withContext(counterCtx) { counter++ } } }  // мутация — на одном потоке
    }
}
counterCtx.close()
```

Работает, но медленно: на **каждое** `counter++` — переключение контекста.

**Грубое (coarse-grained)** — на один поток гоним **весь блок** работы с состоянием:

```kotlin
withContext(counterCtx) {                      // всё внутри — на одном потоке
    coroutineScope { repeat(1000) { launch { counter++ } } }
}
```

Быстрее: переключились один раз. Правило — **замыкай как можно крупнее**.

## 5. `Mutex` — взаимное исключение

`Mutex` (mutual exclusion) — корутинный замок. В критической секции одновременно **не больше одной**
корутины; остальные **приостанавливаются** (не блокируют поток!) и ждут очереди.

```kotlin
val mutex = Mutex()
var counter = 0
withContext(Dispatchers.Default) {
    coroutineScope {
        repeat(1000) { launch { mutex.withLock { counter++ } } }
    }
}
// counter == 1000, всегда
```

- `withLock { }` — берёт замок, выполняет блок, **гарантированно отпускает** (даже при исключении).
  Возвращает значение блока. Всегда предпочитай его ручным `lock()`/`unlock()`.
- Защищает **произвольную** критическую секцию, в т.ч. составные инварианты (перевод между счетами).

> ⚠️ **`Mutex` ≠ `synchronized`.** `synchronized` **блокирует поток** и не дружит с `suspend`.
> `Mutex.withLock` **приостанавливает корутину** — поток свободен под другую работу. Внутри корутин
> для взаимного исключения бери `Mutex`, не `synchronized`.

Два подводных камня:
- **`Mutex` не реентрантный.** Повторный `lock` из той же корутины, уже держащей замок, → **дедлок**.
- **Не держи замок через долгий `suspend`.** Замок сериализует всех ждущих; сетевой вызов под
  замком превращает параллельную работу в очередь. Держи секцию **короткой**.

## 6. Actor — один владелец состояния

Логическое продолжение замыкания: пусть состоянием владеет **ровно одна корутина**, а все остальные
шлют ей **команды через канал**. Никто, кроме владельца, состояния не касается → гонок нет.

```kotlin
sealed interface Msg
data class Inc(val by: Int) : Msg
data class Get(val reply: CompletableDeferred<Int>) : Msg

fun CoroutineScope.counterActor(): SendChannel<Msg> {
    val ch = Channel<Msg>()
    launch {                       // единственный владелец `state`
        var state = 0
        for (msg in ch) when (msg) {
            is Inc -> state += msg.by
            is Get -> msg.reply.complete(state)
        }
    }
    return ch
}
```

Плюс: состояние инкапсулировано, легко расширять протокол. Минус: больше кода; общение через
сообщения. Хорош, когда у состояния сложный жизненный цикл и много типов операций.

## 7. Оптимизация: локальная агрегация вместо блокировки на каждый шаг

Замок на **каждый** элемент — дорого (все воркеры выстраиваются в очередь). Часто лучше: каждый
воркер копит **локальную** сумму без синхронизации, а в общий результат вливает **один раз** под
замком.

```kotlin
val mutex = Mutex(); var total = 0
chunks.map { chunk ->
    launch {
        var local = 0
        for (x in chunk) local += x        // без блокировок — своя переменная
        mutex.withLock { total += local }  // одна блокировка на воркера, не на элемент
    }
}
```

> 🧠 **Правило.** Минимизируй **contention** (борьбу за замок): чем реже и короче захват, тем больше
> реального параллелизма. Локальное накопление + редкий locked-merge — классика.

## 8. Что выбрать

| Ситуация | Бери |
|----------|------|
| один счётчик / флаг / ссылка | **атомик** |
| одна переменная, обновление по условию | **CAS-цикл** (`updateAndGet`/`compareAndSet`) |
| состояние касается только одного места кода | **грубое замыкание** на поток |
| произвольная критическая секция, составной инвариант | **`Mutex.withLock`** |
| состояние + богатый протокол операций | **actor** (канал + один владелец) |
| независимые ключи | **striping**: свой `Mutex`/атомик на ключ |

Практическое правило: **сначала попробуй вообще не делить состояние** (структурная конкурентность,
`async`/`await`, возврат результата). Понадобилось делить — бери **самый простой** подходящий
инструмент из таблицы, а не сразу `Mutex` на всё.
