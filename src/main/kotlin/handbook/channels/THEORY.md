# Тема 8. Каналы (Channel)

## 1. Что такое Channel

`Channel<T>` — **горячий** конвейер для передачи значений между корутинами. По сути это
`suspend`-версия `BlockingQueue`: одна корутина `send`-ит, другая `receive`-ит, но вместо
блокировки потоков — приостановка корутин.

Ключевое отличие от `Flow` (тема 6):
- `Flow` **холодный**: код выполняется на каждый `collect`, один продюсер на подписку.
- `Channel` **горячий**: значения «летят» независимо от того, есть ли получатель; это точка
  встречи, через которую общаются **уже работающие** корутины.

```kotlin
val channel = Channel<Int>()
launch {
    for (x in 1..5) channel.send(x)
    channel.close()               // сигнал «больше не будет»
}
for (y in channel) println(y)     // приём до close()
```

## 2. `send` / `receive` / `close`

- `send(x)` — приостанавливается, если канал полон (backpressure);
- `receive()` — приостанавливается, если канал пуст; бросает при закрытом-и-пустом канале;
- `close()` — закрыть на отправку; после этого получатель дочитает буфер и завершит итерацию;
- `for (x in channel)` / `channel.consumeEach { }` — идиоматичный приём до закрытия.

Безопасные варианты без исключений:
- `trySend(x)` / `tryReceive()` — неблокирующие попытки, возвращают результат-обёртку;
- `receiveCatching()` — вернёт `ChannelResult`, а не бросит на закрытии.

## 3. Ёмкость (capacity)

Задаётся при создании `Channel<T>(capacity)`:

| Ёмкость | Поведение |
|---------|-----------|
| `RENDEZVOUS` (0, по умолчанию) | `send` ждёт, пока кто-то не `receive` (передача «из рук в руки») |
| число / `BUFFERED` | буфер N; `send` не ждёт, пока есть место |
| `CONFLATED` | хранит только **последнее** значение, старое затирается |
| `UNLIMITED` | неограниченный буфер, `send` никогда не ждёт |

`onBufferOverflow` (`SUSPEND` / `DROP_OLDEST` / `DROP_LATEST`) настраивает, что делать при переполнении.

## 4. Билдер `produce`

`produce { }` создаёт корутину-производителя и возвращает `ReceiveChannel`. Канал **закрывается
автоматически** при завершении блока (и при отмене потребителя) — меньше шансов забыть `close()`:

```kotlin
fun CoroutineScope.numbers(): ReceiveChannel<Int> = produce {
    for (i in 1..5) send(i)
}   // канал закроется сам по выходу из блока
```

`produce` — расширение `CoroutineScope`, поэтому вызывается внутри scope.

## 5. Пайплайны (pipelines)

Каналы соединяются в конвейеры: выход одного — вход другого. Каждое звено — своя корутина:

```kotlin
fun CoroutineScope.numbers(): ReceiveChannel<Int> = produce { for (i in 1..5) send(i) }

fun CoroutineScope.square(input: ReceiveChannel<Int>): ReceiveChannel<Int> = produce {
    for (x in input) send(x * x)
}

// использование: square(numbers()) → 1,4,9,16,25
```

Пайплайны хорошо ложатся на многоступенчатую обработку данных, где каждая ступень работает
параллельно с другими.

## 6. Fan-out (веерное распределение)

Несколько потребителей читают из **одного** канала — работа распределяется между ними: каждый
элемент достаётся **ровно одному** получателю. Так масштабируют тяжёлую обработку на воркеров:

```kotlin
val jobs = List(workers) {
    launch { for (item in channel) process(item) }   // конкурируют за элементы
}
```

## 7. Fan-in (веерное слияние)

Несколько производителей пишут в **один** канал:

```kotlin
val merged = Channel<Int>()
launch { for (x in sourceA) merged.send(x) }
launch { for (x in sourceB) merged.send(x) }
```

## 8. Тикер и таймауты (упоминание)

Для периодических событий есть паттерны на каналах, а для получения «первого готового» из
нескольких каналов — `select { onReceive ... }` (см. тему 3, где `select` использовался для
`Deferred`). `select` одинаково работает и с каналами.

## 9. Утечки и отмена

Правила гигиены:
- Тот, кто **получает** из канала, обычно и отвечает за его потребление до конца или отмену.
- `consume { }` / `consumeEach { }` гарантированно закрывают `ReceiveChannel` по завершении
  (в т.ч. при исключении) — предпочтительнее «сырого» `for`, если канал больше не нужен.
- Незакрытый и заброшенный канал с ждущими `send` — утечка. `produce` снимает эту заботу.
- Отмена потребителя отменяет `produce`-производителя (структурная связь).

## 10. Channel или Flow — что выбрать

| Нужно | Бери |
|-------|------|
| холодный источник, декларативные операторы, один потребитель на запуск | **Flow** |
| распределять работу между воркерами (fan-out) | **Channel** |
| передавать события между уже работающими корутинами | **Channel** |
| объединять несколько живых источников (fan-in) | **Channel** |
| наблюдаемое состояние / broadcast на многих | **StateFlow/SharedFlow** (тема 7) |

Практическое правило: **снаружи** отдавай `Flow` (холодный, безопасный), а `Channel` используй
**внутри** как механизм связи корутин. `channel.receiveAsFlow()` / `consumeAsFlow()` мостят одно в другое.
