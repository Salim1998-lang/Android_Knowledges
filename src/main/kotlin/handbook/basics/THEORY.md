## 1. Зачем вообще нужны корутины

Представь сервер, который на каждый запрос ждёт ответа БД 50 мс. На потоках (threads) каждый
ожидающий запрос занимает целый поток ОС (~1 МБ стека, дорогое переключение контекста). 10 000
одновременных запросов = 10 000 потоков = система ложится.

Корутина — это **приостанавливаемое вычисление**. Пока она «ждёт» (БД, сеть, таймер), она
**не занимает поток**: поток освобождается и крутит другие корутины. Поэтому на десятке потоков
можно держать сотни тысяч корутин. Корутина легковесна: это не поток, а объект-состояние.

Ключевое слово — **приостановка (suspension)**: корутина умеет «заморозиться» в точке ожидания,
запомнив, где остановилась, и продолжиться позже — возможно, уже на другом потоке.

## 2. `suspend`-функции

`suspend` помечает функцию, которая **может приостановиться**:

```kotlin
suspend fun loadUser(): User {
    delay(100)          // приостановка: поток свободен эти 100 мс
    return User("Ann")
}
```

Правила:
- `suspend`-функцию можно вызвать **только** из другой `suspend`-функции или из корутины. Это
  проверяет компилятор — «suspend заразен» (suspend colouring).
- Под капотом компилятор превращает `suspend`-функцию в конечный автомат (CPS-трансформация) с
  скрытым параметром `Continuation`. Знать это не обязательно, но полезно понимать, что каждая
  suspend-точка — это возможная граница приостановки.
- Обычный вызов `suspend`-функции выглядит как обычный синхронный вызов — никаких колбэков в коде.
  Это и есть главная выгода: **асинхронный код, читающийся как последовательный**.

## 3. Билдеры корутин

| Билдер | Откуда вызывают | Что делает | Возвращает |
|--------|-----------------|------------|------------|
| `runBlocking { }` | из обычного кода (`main`, тесты) | **блокирует** текущий поток, пока корутина не завершится. Мост «обычный код ↔ suspend-мир». | результат блока |
| `launch { }` | внутри `CoroutineScope` | «выстрелил-и-забыл»: запускает корутину, не возвращая результат | `Job` |
| `async { }` | внутри `CoroutineScope` | запускает корутину, дающую результат (тема 2) | `Deferred<T>` |

```kotlin
fun main() = runBlocking {          // мост в мир корутин
    val job: Job = launch {         // дочерняя корутина, работает конкурентно
        delay(200)
        println("мир")
    }
    println("привет")
    job.join()                      // ждём завершения ребёнка
}
// печать: привет, затем (через 200 мс) мир
```

> `runBlocking` — только для `main`, тестов и мостов из legacy-кода. **Внутри** приложения его
> использовать нельзя: он блокирует поток и убивает весь смысл корутин.

## 4. `CoroutineScope` — где живут корутины

`launch` и `async` — это функции-расширения `CoroutineScope`. Scope — «область», к которой
привязан жизненный цикл корутин: все запущенные в scope корутины — его **дети**. Отмена/завершение
scope распространяется на детей. `runBlocking { }` и `coroutineScope { }` создают scope, внутри
которого доступны `this.launch { }`.

## 5. `Job` — ручка управления корутиной

`launch` возвращает `Job`:
- `job.join()` — `suspend`, приостановиться, пока корутина не завершится;
- `job.cancel()` — отменить (подробно в теме 3);
- `job.isActive` / `job.isCompleted` / `job.isCancelled` — состояние;
- `job.children` — дочерние Job'ы.

Job'ы образуют **дерево**: у дочерней корутины родитель — Job окружающего scope. Это фундамент
структурной конкурентности (тема 2).

### Жизненный цикл Job

```
          start()/join()            тело доиграло
  New ──────────────────► Active ───────────────────► Completed
 (LAZY)                     │
                            │ cancel() / ошибка
                            ▼
                       Cancelling ──────► Cancelled
                    (доигрывает finally)
```

Флаги — это срез состояния:

| Состояние | isActive | isCompleted | isCancelled |
|-----------|:--------:|:-----------:|:-----------:|
| New (LAZY, не стартована) | false | false | false |
| Active | true | false | false |
| Cancelling | false | false | true |
| Cancelled | false | true | true |
| Completed (успех) | false | true | false |

Две ловушки: `isCompleted == true` и при успехе, **и** при отмене (корутина «доехала» до конца в любом
виде — важно не путать с успехом). А `isActive == false` ещё не значит «завершилась»: у ленивой (New)
и у отменяемой (Cancelling) он тоже `false`. `Cancelling` — переходное состояние: отмена запрошена, но
`finally`/cleanup ещё доигрывают (подробно в теме 3).

### Ленивый старт

```kotlin
val job = launch(start = CoroutineStart.LAZY) { work() }
// ...ничего не происходит...
job.start()   // или job.join() — только теперь корутина стартует
```

## 6. `delay` vs `Thread.sleep`

| | приостанавливает | освобождает поток | где применять |
|---|---|---|---|
| `delay(ms)` | корутину | да ✅ | внутри корутин |
| `Thread.sleep(ms)` | поток | нет ❌ | почти никогда в корутинах |

`delay` — `suspend`-функция. `Thread.sleep` блокирует несущий поток, из-за чего другие корутины
на нём встают. Внутри корутин почти всегда нужен `delay`.

**Скрытая опасность на пуле.** На однопоточном диспетчере `Thread.sleep` виден сразу — всё встаёт.
На многопоточном (`Dispatchers.Default`, размер ≈ числу ядер) пара блокирующих вызовов
маскируется: свободные потоки тянут остальные корутины, тест зелёный. Но пул **фиксирован** — как
только число одновременных блокирующих вызовов достигает размера пула, **все** потоки заняты, ни
одна корутина не исполняется (*thread starvation*), throughput падает в ноль. Баг всплывает только
под нагрузкой, в проде. Если блокирующий вызов неизбежен (legacy JDBC, файловый IO) — выноси его на
`Dispatchers.IO` (эластичный пул под блокировки) через `withContext(Dispatchers.IO) { ... }`.

## 7. Конкурентность ≠ параллелизм

- **Конкурентность** — несколько задач *в процессе выполнения* с чередованием. Даже на одном
  потоке `launch { a() }; launch { b() }` дают конкурентность: пока `a` ждёт в `delay`, крутится `b`.
- **Параллелизм** — задачи выполняются *физически одновременно* на нескольких ядрах.

Корутины дают конкурентность всегда; параллелизм — если диспетчер многопоточный (`Dispatchers.Default`).
В тестах (`runTest`) диспетчер **однопоточный** — гонок данных нет, поведение детерминировано.

## 8. Порядок выполнения нескольких `launch`

```kotlin
coroutineScope {
    launch { delay(30); print("A") }
    launch { delay(10); print("B") }
    launch { delay(20); print("C") }
}   // scope ждёт всех троих
// печать: BCA — по возрастанию задержки, а не по порядку запуска
```

Все три `launch` стартуют «почти одновременно», а завершаются по мере готовности. `coroutineScope`
не отдаст управление, пока не завершатся **все** дети.

## 9. Как планируются корутины: очередь и `yield`

`launch { }` **не прерывает** текущий код — он лишь ставит корутину в очередь диспетчера. Ребёнок
начнёт реально работать только когда текущая корутина дойдёт до своей suspend-точки (`delay`,
`join`, `await`, `yield`) или завершит тело. Между двумя suspend-точками код корутины на одном
потоке **атомарен** — его никто не прервёт.

Отсюда правило чтения вывода: печать до первой suspend-точки идёт «пачкой», в порядке кода;
переключение на другие корутины случается ровно **в** точке приостановки, не раньше.

`yield()` — suspend-точка, которая **ничего не ждёт**: просто уступает поток другим готовым
корутинам из очереди и встаёт в её хвост.

```kotlin
coroutineScope {
    launch { print("1"); yield(); print("3") }
    launch { print("2"); yield(); print("4") }
}
// печать: 1234 — yield заставляет корутины чередоваться в точке уступки
```

Без `yield` каждая `launch`-корутина без внутренних suspend-точек отработала бы **целиком** до
передачи управления → `1324`. `yield` нужен, чтобы длинный CPU-цикл не монополизировал поток (и как
точка проверки отмены — тема 3).

## 10. Тестирование корутин: `runTest` и виртуальное время

`kotlinx-coroutines-test` даёт `runTest { }` — как `runBlocking`, но с **виртуальным временем**:
`delay(1000)` не ждёт реально секунду — планировщик «проматывает» время мгновенно. Тесты быстрые
и детерминированные.

```kotlin
@Test
fun example() = runTest {
    val result = greet("Kotlin")   // delay внутри проматывается мгновенно
    assertEquals("Привет, Kotlin!", result)
}
```

Полезные инструменты внутри `runTest`:
- `currentTime` — сколько виртуальных миллисекунд «прошло»;
- `advanceTimeBy(ms)` — промотать время на `ms`;
- `advanceUntilIdle()` — промотать, пока есть отложенные задачи;
- `runCurrent()` — выполнить задачи, запланированные на текущий момент.

## 11. Частые ошибки новичка

- **`Thread.sleep` в корутине** — блокирует поток, ломает конкурентность.
- **`runBlocking` внутри suspend-функции** — почти всегда ошибка; нужен `coroutineScope`.
- **`GlobalScope.launch`** — корутина вне структуры, живёт «сама по себе», её легко потерять и
  не отменить. Избегай (кроме очень редких случаев).
- **Забыть `join`/`await`** — родитель может уйти раньше, чем ребёнок доделает (если scope не
  структурный).
