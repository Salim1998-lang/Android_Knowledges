# Тема 2. Структурная конкурентность

## 1. Проблема, которую решает структурная конкурентность

Без дисциплины асинхронный код порождает «утёкшие» задачи: запустили фоновую работу и потеряли
её — она крутится в никуда, жрёт ресурсы, её невозможно отменить, её ошибки теряются. Классика:
`GlobalScope.launch { ... }` — корутина без владельца.

**Структурная конкурентность** (structured concurrency) вводит правило: у каждой корутины есть
родитель (scope), и **родитель не завершится, пока не завершатся все его дети**. Отсюда три
гарантии:
1. Нет потерянных корутин — область жизни явная и ограниченная.
2. Ошибка ребёнка не теряется — она всплывает к родителю.
3. Отмена родителя отменяет всех детей (и наоборот, ошибка ребёнка отменяет родителя и сиблингов).

Это как блочная структура кода (`{ }`): вход в блок → выход из блока только после того, как всё
внутри отработало. Только теперь «внутри» — параллельные корутины.

## 2. `coroutineScope { }`

Ключевой `suspend`-билдер. Создаёт новый scope и **ждёт всех детей**, запущенных внутри. Возвращает
результат только когда все `launch`/`async` внутри завершились:

```kotlin
suspend fun loadDashboard(): Dashboard = coroutineScope {
    val user = async { loadUser() }   // стартует немедленно
    val feed = async { loadFeed() }   // стартует немедленно, параллельно
    Dashboard(user.await(), feed.await())
}   // сюда попадём только когда ОБА async завершились
```

Отличие от `runBlocking`: `coroutineScope` **не блокирует поток** — он приостанавливает
вызывающую корутину. Это правильный способ «сгруппировать» параллельную работу внутри
suspend-функции.

## 3. `async` / `await` / `awaitAll`

`async { }` возвращает `Deferred<T>` — «обещание» результата:

```kotlin
val deferred: Deferred<Int> = async { compute() }
val value: Int = deferred.await()   // приостановиться до готовности
```

- Корутина `async` стартует **немедленно** (по умолчанию `CoroutineStart.DEFAULT`).
- `await()` приостанавливается, пока результат не готов, и **перебрасывает** исключение, если
  `async` упал.
- `listOf(d1, d2, d3).awaitAll()` — дождаться всех и получить `List<T>`; при первой ошибке —
  падает и отменяет остальные.

### `launch` vs `async`

| | возвращает | когда нужен |
|---|---|---|
| `launch` | `Job` | побочный эффект, результат не нужен |
| `async` | `Deferred<T>` | нужен результат вычисления |

Не используй `async { }` без `await()` — исключение из такого `async` может потеряться (оно ждёт
`await`, которого нет). Если результат не нужен — бери `launch`.

## 4. Ленивый `async` (`CoroutineStart.LAZY`)

По умолчанию `async` стартует немедленно. С `start = CoroutineStart.LAZY` корутина **не запустится**,
пока её явно не разбудят через `start()` или `await()`:

```kotlin
val d = async(start = CoroutineStart.LAZY) { compute() }
// здесь ещё ничего не считается
d.start()          // запустить и не ждать (fire, но привязан к scope)
val x = d.await()  // или сразу await — тоже запустит, затем дождётся
```

Зачем: отложить старт до момента, когда результат точно понадобится, или выстроить порядок запуска
вручную. Ловушка: если по ветке кода не вызвать **ни** `start()`, **ни** `await()` — корутина не
выполнится вовсе, а `coroutineScope` всё равно будет ждать её как «непущенного» ребёнка и зависнет.
Ленивый `launch` — в теме «Основы».

## 5. Последовательно vs параллельно — цена ошибки

```kotlin
// ПОСЛЕДОВАТЕЛЬНО: 200 мс (100 + 100)
suspend fun slow(): Pair<A, B> {
    val a = loadA()   // ждём 100 мс
    val b = loadB()   // потом ещё 100 мс
    return a to b
}

// ПАРАЛЛЕЛЬНО: ~100 мс
suspend fun fast(): Pair<A, B> = coroutineScope {
    val a = async { loadA() }   // обе стартуют разом
    val b = async { loadB() }
    a.await() to b.await()
}
```

Частая ошибка: `async { }.await()` сразу в одной строке для каждой задачи — это опять
последовательно! Сначала запусти **все** `async`, потом делай `await`.

## 6. Параллельная декомпозиция коллекций

```kotlin
suspend fun <T, R> parallelMap(items: List<T>, f: suspend (T) -> R): List<R> = coroutineScope {
    items.map { item -> async { f(item) } }   // запустили все
         .awaitAll()                          // собрали в порядке items
}
```

`awaitAll()` **сохраняет порядок** входного списка независимо от того, кто из корутин закончил
раньше. Это важнейший инструмент «map, но параллельно».

## 7. `coroutineScope` vs `supervisorScope`

- `coroutineScope`: падение **любого** ребёнка отменяет остальных и пробрасывает исключение
  (fail-fast). Нужен, когда результаты взаимозависимы: нет смысла ждать остальных, если один упал.
- `supervisorScope`: дети **независимы** — падение одного не трогает остальных. Нужен, когда
  каждый результат самоценен (несколько виджетов, несколько источников). Подробно — в теме 4.

```kotlin
supervisorScope {
    val a = async { mayFail() }
    val b = async { alsoWork() }   // выживет, даже если a упал
    // ошибку a перехватываем при a.await() в try/catch
}
```

## 8. Ограничение параллелизма: `Semaphore`

Нельзя запускать 10 000 сетевых запросов разом — сервер/память не выдержат. `Semaphore(permits)`
из `kotlinx.coroutines.sync` ограничивает число одновременно работающих корутин:

```kotlin
suspend fun <T, R> mapConcurrent(items: List<T>, limit: Int, f: suspend (T) -> R): List<R> =
    coroutineScope {
        val gate = Semaphore(limit)
        items.map { item ->
            async { gate.withPermit { f(item) } }   // не более limit одновременно
        }.awaitAll()
    }
```

`withPermit { }` захватывает разрешение перед блоком и гарантированно освобождает после (даже при
исключении).

## 9. Диспетчеры (краткое знакомство)

`CoroutineContext` несёт диспетчер — где исполняется корутина:
- `Dispatchers.Default` — пул под CPU-задачи (размер ≈ числу ядер);
- `Dispatchers.IO` — большой пул под блокирующий IO;
- `Dispatchers.Main` — UI-поток (Android/Swing/JavaFX);
- `Dispatchers.Unconfined` — без привязки (редко).

Сменить контекст: `withContext(Dispatchers.IO) { blockingRead() }`. Подробнее — в дальнейших темах;
в тестах диспетчер подменяется на виртуальный автоматически.

## 10. `coroutineScope` vs `withContext`

Оба **приостанавливают** вызывающую корутину и возвращают управление только когда блок отработал.
Оба пробрасывают ошибки детей и кооперативно отменяемы. Разница в назначении:

- `coroutineScope { }` — **тот же** контекст; задача: сгруппировать **параллельных** детей
  (`launch`/`async`) и дождаться всех. Про конкурентность.
- `withContext(ctx) { }` — **сменить** контекст (обычно диспетчер) для **одного** участка и вернуть
  его результат. Про «где исполнять», а не про разветвление.

```kotlin
suspend fun read(): Data = withContext(Dispatchers.IO) {
    blockingDbRead()             // один блок на другом диспетчере
}

suspend fun readBoth(): Pair<Data, Data> = coroutineScope {
    val a = async { read() }     // разветвление на параллельные дети
    val b = async { read() }
    a.await() to b.await()
}
```

Правило: нужен другой диспетчер для одного участка → `withContext`. Нужно запустить несколько
корутин и дождаться → `coroutineScope`. Частая ошибка — `withContext` вокруг двух `async` в надежде
на параллелизм: разветвление даёт `async`, а не `withContext`.

## 11. Собственный `CoroutineScope` (вне suspend-функций)

Для «долгоживущих» владельцев (ViewModel, сервис) создают scope-поле:

```kotlin
class Service {
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)
    fun start() = scope.launch { work() }
    fun stop() = scope.cancel()   // отменит всё, что запустили
}
```

Правило: **кто создал scope — тот его и отменяет**. Иначе — утечка.

## 12. Что ломает структурность: анти-паттерны

Структурность держится на связи родитель↔ребёнок через `Job`. Её легко разорвать:

1. **`GlobalScope`** — корутина без родителя (см. §1). Не отменяется вместе с вызывающим, её ошибки
   уходят в никуда. Почти всегда — ошибка проектирования.

2. **Передача чужого `Job` в билдер.** `launch(Job()) { }` внутри scope создаёт корутину с **новым**
   родителем вместо текущего scope — она отвязывается от структуры:

```kotlin
coroutineScope {
    launch(Job()) { work() }   // ← отвязалась: scope её НЕ ждёт и НЕ отменяет
}   // выйдем отсюда, не дождавшись work() → утечка
```

   Правильно — не подсовывать `Job()`/`SupervisorJob()` в билдер ребёнка. Нужна супервизор-семантика
   — бери `supervisorScope` (§7), который остаётся частью дерева.

3. **`CoroutineScope`-поле без `cancel()`.** Создал scope (§11) — обязан его отменить, иначе дети
   переживут «владельца». Кто создал — тот и отменяет.

Мнемоника: как только у корутины появился `Job`, отличный от родительского scope, структурная
конкурентность для неё выключена — за её жизнь и смерть теперь отвечаешь ты сам.

## 13. Итоговая ментальная модель

- `coroutineScope { }` = «запусти это параллельно и дождись всего».
- `async { } ... await()` = «посчитай параллельно, результат заберу позже».
- `awaitAll()` = «дождись всех, сохрани порядок».
- `withContext(ctx) { }` = «сделай это здесь, но на другом диспетчере» (один блок, не разветвление).
- Ошибка внутри = fail-fast (или изоляция через `supervisorScope`).
- Чужой `Job` в билдере / `GlobalScope` = структурность выключена, отвечаешь сам.
