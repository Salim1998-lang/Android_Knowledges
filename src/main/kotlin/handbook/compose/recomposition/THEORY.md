# Тема 1. Рекомпозиция (что и почему Compose перерисовывает)

> Это фундамент всего Compose. UI в Compose — **функция от состояния**: `UI = f(state)`. Когда
> состояние меняется, Compose заново вызывает затронутые `@Composable`-функции, чтобы привести
> дерево к новому состоянию. Этот повторный вызов и есть **рекомпозиция**. Пока не понимаешь, ЧТО
> именно триггерит рекомпозицию и ПОЧЕМУ перерисовывается не весь экран, — не понимаешь ни лишних
> рекомпозиций, ни skipping, ни стабильности.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.recomposition.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Мы моделируем механику Compose-рантайма детерминированно на JVM (тип [`Node`](Model.kt) — узел
> дерева композиции = recomposition scope) — без Compose-рантайма и Android. Идеи 1:1 переносятся на
> настоящий `androidx.compose.runtime`.

## 1. UI = f(state): что такое рекомпозиция

Императивный UI (`View`): ты сам вызываешь `textView.setText(...)`, `view.setVisibility(...)` — вручную
синхронизируешь виджеты с данными. Декларативный UI (Compose): ты **описываешь**, как выглядит экран
для текущего состояния, а рантайм сам решает, что перерисовать при изменении.

```kotlin
@Composable
fun Counter(count: Int) {
    Text("Кликов: $count")   // описание, а не команда «поменяй текст»
}
```

Когда `count` меняется, Compose **заново вызывает** `Counter` с новым значением — это рекомпозиция.
Первый вызов называется **композицией** (initial composition), последующие — рекомпозициями.

Ключевое: рекомпозиция должна быть **дешёвой и частой**, поэтому Compose старается перевызывать
**как можно меньше** функций — только те, чей результат мог измениться.

## 2. Snapshot state и read tracking

Рекомпозицию триггерит не любое присваивание, а изменение **наблюдаемого состояния** — объекта
`State`/`MutableState` (создаётся `mutableStateOf`, `remember { … }`, и т.п.):

```kotlin
var count by remember { mutableStateOf(0) }   // наблюдаемое состояние
Text("$count")                                 // ЧТЕНИЕ count здесь регистрируется
```

Во время композиции рантайм включает **read tracking**: каждый раз, когда scope читает `State`, он
записывается как **читатель** этого состояния. Формируется read-set scope'а. → задачи **Л1, Л3, Л4**.

Обычная переменная (`var count = 0`) состоянием НЕ является: её изменение никто не отслеживает, и UI
не перерисуется. Это самый частый баг новичка. Отсюда же: если у состояния нет ни одного читателя,
запись в него ничего не перерисует — состояние «в никуда». → задача **Л4**.

## 3. Инвалидация: запись меняет только читателей

Когда значение `State` меняется, рантайм **инвалидирует ровно те scope'ы, которые его читали**, и
ставит их в очередь на рекомпозицию. Это **fine-grained recomposition**: перерисовывается не всё
дерево, а точечно — сколько бы ни было `@Composable` на экране. → задачи **Л1, Л5**.

Важная тонкость — **равенство**. Присваивание структурно РАВНОГО значения (`old == new`) —
**no-op**: инвалидации не будет.

```kotlin
count = count          // ничего не произойдёт
list = list.toList()   // НОВЫЙ объект (!=) → инвалидация, даже если содержимое то же
```

Поэтому `state.value = state.value` бесполезно, а «пересоздать список с тем же содержимым» —
наоборот, вызовет лишнюю рекомпозицию. → задача **Л2**.

## 4. Recomposition scope и restartable-функции

Не у каждого `@Composable` есть собственная «точка перезапуска». Своим **RecomposeScope** обладают
только **restartable**-функции (обычные `@Composable fun … : Unit`). А **inline**-функции —
`Column`, `Row`, `Box`, `forEach { }` — своего scope не имеют: их тело встраивается в вызывающего.

Следствие: если состояние читается **внутри inline-обёртки**, инвалидация **поднимается** до
ближайшей restartable-функции — и рекомпозируется она целиком.

```kotlin
@Composable
fun Screen() {          // restartable scope
    Column {            // inline — своего scope НЕТ
        Text("$count")  // читает count здесь → инвалидируется Screen целиком
    }
}
```

Чтобы сузить область рекомпозиции, чтение состояния выносят в отдельную маленькую restartable-функцию
(или откладывают чтение — см. тему «Фазы кадра»). → задачи **Л7, Л8, С9, С10**.

## 5. Skipping: как Compose пропускает неизменившееся

Когда родитель рекомпозируется, он заново «вызывает» своих детей. Но Compose **пропускает** (skip)
ребёнка, если выполнены два условия:
1. функция **skippable**, и
2. **все её аргументы не изменились** (равны прошлым по `equals`).

Пропущенный `@Composable` не выполняется вообще — вместе со всем своим поддеревом. → задачи **Л6,
С11, С12, СЛ17**.

```kotlin
@Composable fun Parent() {
    val count by remember { mutableStateOf(0) }
    Header(title = "Static")   // title не меняется → Header пропускается при рекомпозиции Parent
    Counter(count = count)     // count изменился → Counter рекомпозируется
}
```

**Skippable** функция становится, если рантайм уверен, что может сравнить её параметры, — то есть все
параметры **стабильны** (см. п. 6). Один нестабильный параметр делает функцию **неskippable**: она
рекомпозируется **всегда**, когда рекомпозируется родитель. → задача **С13**.

## 6. Стабильность (stability) — почему пропуск вообще возможен

Тип **стабилен**, если Compose гарантированно узнаёт об изменениях его публичного состояния и
`equals` согласован. Стабильны: примитивы, `String`, функциональные типы, `@Stable`/`@Immutable`
типы, `State<T>`. Нестабильны: `List`/`Set`/`Map` (интерфейсы — реализация может быть мутабельной),
классы из других модулей без метки, `var`-поля в `data class`.

- `data class User(val id: Int, val name: String)` — стабилен (все поля стабильны, `val`).
- `data class Page(val items: List<Item>)` — **нестабилен** (`List` нестабилен) → `Page`-параметр
  делает функцию неskippable. Лечение: `kotlinx.collections.immutable` (`ImmutableList`), обёртка
  `@Immutable`, либо `@Stable`.

Стабильность параметров — это то, что превращает функцию в skippable. Подробно — в теме
«Производительность»; здесь достаточно правила: **все параметры стабильны ⇒ функция skippable**.
→ задача **С13**.

## 7. Условные чтения меняют read-set

Read-set пересобирается на КАЖДОЙ рекомпозиции. Если из-за ветвления scope перестал читать какое-то
состояние — он больше не будет инвалидироваться его изменениями (пока снова не начнёт читать):

```kotlin
if (expanded) Text("$count")   // когда expanded=false, count НЕ читается →
                               // изменения count не будят этот scope
```

Это и мощно (меньше лишних рекомпозиций), и коварно (кажется, что «не обновляется»).
→ задача **С14**.

## 8. `derivedStateOf`: гасим шум частых изменений

Иногда вход меняется часто, а нужный **вывод** — редко. Классика: скролл. `firstVisibleItemScrollOffset`
меняется на каждый пиксель, но `showButton = offset > 0` меняется лишь дважды за всю прокрутку.

```kotlin
val showButton by remember {
    derivedStateOf { listState.firstVisibleItemScrollOffset > 0 }
}
```

`derivedStateOf` пересчитывается при изменении входа, но **инвалидирует читателей только если
поменялся его РЕЗУЛЬТАТ**. Так частый «шум» входа не превращается в поток рекомпозиций.
→ задача **СЛ19**.

## 9. Полный цикл: state → инвалидация вверх → рекомпозиция вниз

Собираем воедино один проход рекомпозиции при изменении состояния:

1. **Инвалидация.** Находим читателей изменённого состояния и **поднимаем** каждого до его
   restartable-scope (`recomposeTargets`). Это узлы, которые встанут в очередь. → **С10**.
2. **Рекомпозиция вниз.** Каждый такой scope выполняется заново и перевызывает детей; стабильные
   дети с неизменившимися параметрами **пропускаются** вместе с поддеревом, остальные рекомпозируются
   и спускаются дальше (`recompose`). → **С11, СЛ16**.

Так один `setValue` превращается в точечный, минимальный объём повторной работы. → задача **СЛ16**.

## 10. Лишние рекомпозиции и горячие точки

Диагностика производительности Compose — это, по сути, поиск scope'ов, которые рекомпозируются
**слишком часто** или **напрасно**. Считаем, сколько раз каждый scope инвалидируется за серию
изменений, и ищем «горячие точки» (`recompositionHotspots`) — кандидаты на:
- вынос состояния ниже (сузить scope), чтобы не тянуть за собой полдерева;
- `derivedStateOf` — погасить частый вход;
- стабилизацию параметров (`@Immutable`, `ImmutableList`, `remember` для лямбд) — вернуть skipping;
- **deferred reads** — читать состояние в фазе layout/draw, а не composition (тема «Фазы кадра»).

Инструменты в реальном проекте: **Layout Inspector** (счётчики recomposition/skip count) и
**Compose Compiler Metrics** (какие функции restartable/skippable/stable). → задачи **СЛ18, СЛ20**.
