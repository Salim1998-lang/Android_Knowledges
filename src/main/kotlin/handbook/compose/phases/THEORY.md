# Тема 8. Фазы кадра (Composition → Layout → Drawing, отложенное чтение)

> Каждый кадр Compose проходит через **три фазы, строго по порядку**:
> **Composition** («что показывать»), **Layout** («где и какого размера»), **Drawing** («как
> нарисовать»). Понимание фаз — это ключ к производительности: изменение состояния перезапускает
> только ту фазу, в которой это состояние **читается**, и все последующие; более ранние фазы
> **пропускаются**. Отсюда практический приём — **отложенное чтение**: читать состояние как можно
> позже (в layout или drawing), чтобы пропустить рекомпозицию, а иногда и раскладку.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.phases.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику моделируем детерминированно на JVM: фаза [`Phase`](Model.kt) и читающий состояние
> модификатор [`ReadingModifier`](Model.kt). Идеи 1:1 переносятся на реальный Compose.

## 1. Три фазы кадра

```
STATE ──▶ COMPOSITION ──▶ LAYOUT ──▶ DRAWING ──▶ на экран
          «что»            «где/размер»   «как»
```

- **Composition** — выполняются composable-функции, строится/обновляется дерево UI: *что* показывать.
- **Layout** — каждый узел измеряется (measure) и размещается (place): *где* и *какого размера*.
- **Drawing** — узлы рисуют себя на canvas: *как* выглядят.

Порядок фиксирован и однонаправлен: composition → layout → drawing. → задачи **Л1, Л2, Л3, Л4, Л5**.

## 2. Правило инвалидации: «от фазы чтения и далее»

Compose отслеживает, **в какой фазе читается** каждое состояние. При изменении состояния
перезапускается фаза, где оно читается, и **все последующие**; предыдущие — пропускаются.

| Где читается состояние | Что перезапустится | Что пропущено |
|------------------------|--------------------|---------------|
| Composition           | composition + layout + drawing | — |
| Layout                | layout + drawing   | composition |
| Drawing               | drawing            | composition + layout |

Пример: `Text("$counter")` читает `counter` в композиции → полный конвейер. А
`Modifier.graphicsLayer { alpha = fade }` читает `fade` в drawing → перерисовка без рекомпозиции и
раскладки. → задачи **Л6, Л7, С10, С11**.

Если состояние читается в **нескольких** фазах, инвалидация начинается с **самой ранней** из них
(остальные всё равно попадают под «и далее»). → задача **С9**.

## 3. Отложенное чтение (deferred reads)

Главный приём темы: перенести чтение состояния в более позднюю фазу — тогда ранние фазы пропускаются.

```kotlin
// плохо: читаем offset в композиции → рекомпозиция каждый кадр анимации
Box(Modifier.offset(x = animatedDp))

// лучше: лямбда откладывает чтение в layout → композиция пропущена
Box(Modifier.offset { IntOffset(animatedPx, 0) })

// ещё лучше для трансформаций: graphicsLayer читает в drawing → пропущены и composition, и layout
Box(Modifier.graphicsLayer { translationX = animatedPx; alpha = fade })
```

Разница между `offset(x = ...)` и `offset { ... }` — не косметика: lambda-версия существует именно для
того, чтобы отложить чтение. То же с `drawBehind { }` и `graphicsLayer { }` — чтение в фазе
отрисовки. → задачи **Л8, С12, С13, СЛ18**.

**Правило большого пальца:** анимируешь позицию — `offset { }`; анимируешь alpha/scale/rotation/
translation — `graphicsLayer { }`. Так анимация не трогает composition.

## 4. Цена изменения и экономия

Стоимость одного изменения = сумма стоимостей инвалидированных фаз. Composition — самая дорогая фаза
(выполнение кода, аллокации, сравнения), поэтому её пропуск даёт наибольший выигрыш.

За анимацию (изменение каждый кадр, 60/120 кадров в секунду) разница множится на число кадров:
чтение в composition против чтения в drawing — это десятки лишних рекомпозиций в секунду.
→ задачи **С14, С15, СЛ17, СЛ19**.

## 5. Частые ошибки

- **Чтение `scrollState.value` / размера в композиции.** `Text("${scroll.value}")` или логика в теле
  composable по позиции скролла рекомпозирует на каждый пиксель прокрутки. Читай в модификаторе-лямбде
  или через `derivedStateOf` (тема 2).
- **`onGloballyPositioned` → `setState` → рекомпозиция.** Читать результат layout и писать в состояние,
  которое снова читается в композиции, — риск петли «layout → composition → layout».
- **Ненужная передача состояния в композицию.** Значение, которое нужно только для отрисовки, не должно
  участвовать в композиции.

→ задачи **СЛ16, СЛ20** (прогон кадров и таймлайн: какие фазы реально выполнятся при разных изменениях).

## 6. Связь с другими темами

- **Тема 1 (рекомпозиция).** Composition — первая фаза; skipping и fine-grained инвалидация решают,
  выполнится ли она вообще.
- **Тема 2 (состояние) и `derivedStateOf`.** Инструмент, чтобы не тащить «сырое» состояние в композицию.
- **Тема 6 (раскладка) и тема 7 (модификаторы).** Layout-фаза — это measure/place из темы 6; lambda-
  модификаторы из темы 7 — механизм отложенного чтения.
- **Тема 9 (производительность).** Фазы + стабильность = полная картина того, почему UI тормозит.
