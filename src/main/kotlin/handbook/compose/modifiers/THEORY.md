# Тема 7. Модификаторы (порядок цепочки, свёртка, `Modifier.Node`, семантика)

> `Modifier` украшает и настраивает composable: размер, отступы, фон, клики, семантику. Но это не
> «мешок опций», а **упорядоченный неизменяемый список**, который Compose сворачивает и применяет
> строго по порядку. Отсюда главная мысль темы: **порядок модификаторов меняет результат**.
> `padding().background()` и `background().padding()` выглядят по-разному; `padding().clickable()`
> кликается не так, как `clickable().padding()`. Плюс новая система `Modifier.Node` — про то, как
> модификаторы живут и переиспользуются между рекомпозициями.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.modifiers.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику моделируем детерминированно на JVM: элемент цепочки [`Element`](Model.kt) и список как
> цепочка. Идеи 1:1 переносятся на `androidx.compose.ui.Modifier`.

## 1. `Modifier` — упорядоченный список, а не набор флагов

`Modifier.padding(8.dp).background(Color.Red).clickable { }` — это **связанный список** из трёх
элементов в порядке написания. Каждый `.foo()` возвращает НОВЫЙ `Modifier` = «предыдущий + этот
элемент». Порядок сохраняется и определяет всё дальнейшее. Первый в цепочке — самый **внешний**,
последний — самый **внутренний** (ближе к контенту). → задачи **Л1, Л3, Л4**.

## 2. Моноид: `then` и пустой `Modifier`

`Modifier` образует **моноид**:
- **единица** — пустой `Modifier` (компаньон): `Modifier.then(m) == m == m.then(Modifier)`;
- **ассоциативная операция** — `then` (склейка цепочек).

```kotlin
val base = Modifier.padding(8.dp)
val full = base.then(Modifier.background(Color.Red))   // склейка
Modifier                                               // единица: ничего не делает
```

Поэтому модификаторы легко выносить в переменные, собирать условно и переиспользовать — склейка не
теряет порядок. → задачи **Л2, СЛ20**.

## 3. Свёртка (fold): `foldIn` и `foldOut`

Внутри Compose сворачивает цепочку, обходя элементы:
- `foldIn` — слева направо (внешний → внутренний), как написано; → задача **Л4**;
- `foldOut` — справа налево (внутренний → внешний). → задача **С13**.

Разные фазы используют разное направление: constraints спускаются вниз по `foldIn`, а размеры/отрисовка
«всплывают» по `foldOut`. Именно двунаправленность и делает порядок значимым.

## 4. Порядок и размер: constraints вниз, размер вверх

Каждый layout-модификатор (тема 6) преобразует constraints, идущие ВНИЗ, и размер, идущий ВВЕРХ:

```
Modifier.size(100).padding(10)     // size снаружи, padding внутри
  вниз: size задаёт 100 → padding отдаёт контенту 100-20 = 80
  вверх: контент → padding = +20 = 100 → size фиксирует 100     ⇒ футпринт 100, контент 80

Modifier.padding(10).size(100)     // padding снаружи, size внутри
  вниз: padding отдаёт size (100), size фиксирует 100
  вверх: size = 100 → padding = +20 = 120                       ⇒ футпринт 120, контент 100
```

Тот же набор модификаторов, разный порядок — разный и внешний размер, и место под контент. → задачи
**С9, С10, СЛ16**.

## 5. Порядок и отрисовка/ввод: фон и клики

Порядок так же меняет отрисовку и обработку ввода, потому что модификатор действует на всё, что
**внутри** него по цепочке:

- `background().padding()` — фон снаружи → заливка покрывает и область паддинга;
  `padding().background()` — фон внутри → заливается только под контентом (паддинг остаётся пустым).
  → задача **С11**.
- `clickable().padding()` — кликается вся область, включая паддинг; `padding().clickable()` — клик
  только по контенту (паддинг «мёртвый»). → задача **С12**.

Это одна из самых частых причин «выглядит/кликается не так» — и типичный вопрос на собеседовании.

## 6. `Modifier.Node`: жизнь модификатора между рекомпозициями

Современные модификаторы реализованы через **`Modifier.Node`** + `ModifierNodeElement`:
- **Element** — неизменяемое описание (параметры), участвует в сравнении;
- **Node** — долгоживущий объект с состоянием и жизненным циклом (`onAttach`/`onDetach`), который
  Compose создаёт и **переиспользует**.

При рекомпозиции Compose сравнивает новый Element со старым по `equals`:
- **равны** → узел переиспользуется как есть;
- **тот же тип, другие параметры** → узел **обновляется на месте** (`update`), без пересоздания;
- **другой тип** → старый `detach`, новый `attach`;
- **исчез/появился** → `detach` / `attach`.

→ задачи **С14, С15, СЛ18**.

Почему это важно: старый `Modifier.composed { }` пересоздавал состояние на КАЖДОЙ рекомпозиции,
ломал skipping и стоил дорого. `Modifier.Node` держит состояние в узле и переиспользует его — быстрее
и корректнее. → задача **СЛ19**.

Практический вывод: не собирай кастомную логику модификатора через `composed`; используй
`Modifier.Node`/`ModifierNodeElement` (или готовые фабрики). А element должен иметь корректные
`equals`/`hashCode` — иначе узлы будут зря пересоздаваться.

## 7. Семантика: дерево доступности

`Modifier.semantics { }` навешивает **семантическое дерево** — то, что видят TalkBack и UI-тесты
(роль, подпись, состояние). Два ключевых режима:
- `mergeDescendants = true` — узел **сливает** свою семантику с семантикой потомков в один
  доступный элемент (например, кнопка из иконки + текста читается как одно целое); → задача **СЛ17**;
- `clearAndSetSemantics { }` — заменяет семантику поддерева на явно заданную (скрывает внутренние
  узлы от доступности).

Семантика собирается из всех `semantics`-элементов цепочки. → задачи **Л8, СЛ17**.

## 8. Связь с другими темами

- **Тема 6 (раскладка).** Layout-модификаторы — узлы, преобразующие constraints и размер; порядок в
  цепочке — прямое продолжение measure/place.
- **Тема 1 (рекомпозиция).** `Modifier.Node` и корректный `equals` элемента влияют на переиспользование
  и на то, не ломается ли skipping (нестабильный модификатор = лишние рекомпозиции).
- **Тема 9 (производительность).** Лямбды в модификаторах (`clickable { }`) без запоминания —
  источник нестабильности; узловая система и `remember` это лечат.
