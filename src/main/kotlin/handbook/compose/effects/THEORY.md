# Тема 4. Эффекты (`LaunchedEffect`, `DisposableEffect`, `SideEffect`, scope, `rememberUpdatedState`)

> Композиция должна быть **чистой**: `@Composable` может вызываться много раз, в любом порядке, на
> разных потоках, и его нельзя «выполнять ради побочного эффекта». Но приложению нужны эффекты:
> запустить корутину, подписаться на колбэк, тронуть не-Compose API. Для этого есть **effect
> handlers** — они дают побочным эффектам предсказуемый **жизненный цикл**, привязанный к
> композиции: запуск при входе, очистка при выходе, перезапуск при смене ключа. Непонимание этого
> цикла — источник утечек, гонок и «эффект не видит новых данных».
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.effects.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику моделируем детерминированно на JVM: событие жизненного цикла [`EffectEvent`](Model.kt)
> (START/DISPOSE) и последовательности кадров. Идеи 1:1 переносятся на `androidx.compose.runtime`.

## 1. Зачем нужны эффекты и почему нельзя «просто в теле»

Побочный эффект прямо в теле composable — баг: он выполнится на КАЖДОЙ рекомпозиции, в
неопределённый момент и без очистки.

```kotlin
@Composable
fun Screen(userId: String) {
    viewModel.load(userId)   // ❌ выполнится на каждой рекомпозиции; гонки, лишние запросы
    Text(...)
}
```

Эффект-хендлеры решают это: они дают точки «выполнить при входе в композицию», «очистить при
выходе», «перезапустить при смене входа».

## 2. `LaunchedEffect(key)`: корутина с жизненным циклом

`LaunchedEffect` запускает корутину, когда входит в композицию, и **отменяет** её, когда выходит.
При рекомпозиции:
- **ключ не изменился** → корутина продолжает работать (эффект НЕ перезапускается);
- **ключ изменился** → старая корутина отменяется, запускается новая.

```kotlin
LaunchedEffect(userId) {           // при смене userId: отмена старой загрузки + новая
    val user = repo.load(userId)
    state = user
}
```

- `LaunchedEffect(Unit)` / `LaunchedEffect(true)` — стартует **один раз** за время жизни в
  композиции. → задачи **Л3, С13**.
- Смена ключа = «перезапусти эффект под новый вход». → задачи **Л1, С15, СЛ20**.

Жизненный цикл в терминах модели ([`EffectEvent`](Model.kt)): вход → `START`; смена ключа →
`DISPOSE` + `START`; выход → `DISPOSE`. → задачи **Л4, Л5, Л6, С9–С12, СЛ16**.

## 3. `DisposableEffect(key)`: эффект с очисткой

Когда эффекту нужна **очистка** (отписка от колбэка, освобождение ресурса), берут `DisposableEffect`.
Он обязан вернуть `onDispose { }`, который вызывается при выходе из композиции и **перед**
перезапуском при смене ключа:

```kotlin
DisposableEffect(lifecycleOwner) {
    val observer = LifecycleEventObserver { _, event -> /* … */ }
    lifecycleOwner.lifecycle.addObserver(observer)
    onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }  // симметричная очистка
}
```

Жизненный цикл идентичен `LaunchedEffect`, только `START` = выполнить блок, `DISPOSE` = вызвать
`onDispose`. → задачи **С9, СЛ20**.

**Гарантия порядка:** при смене ключа сначала полностью отрабатывает `onDispose` старого, потом
запускается новый блок — никогда наоборот. → задачи **Л4, СЛ18**.

## 4. `SideEffect`: после каждой успешной композиции

`SideEffect { }` выполняется **после каждой успешной (ре)композиции**. У него нет ключей и нет
очистки. Он нужен, чтобы **опубликовать** значение Compose-состояния в объект, живущий вне Compose:

```kotlin
SideEffect {
    analytics.setUserProperty(user.tier)   // синхронизируем не-Compose объект с текущим состоянием
}
```

Отличие от `LaunchedEffect(Unit)`: тот — один раз, `SideEffect` — каждый раз. → задачи **Л2, С13**.

## 5. `rememberCoroutineScope()`: запуск корутин из событий

`LaunchedEffect` стартует из **композиции**. Но корутину часто нужно запустить из **обработчика
события** (клик) — вне композиции. Для этого `rememberCoroutineScope()` даёт `CoroutineScope`,
привязанный к точке композиции: он живёт, пока композиция в дереве, и **отменяется при выходе**.

```kotlin
val scope = rememberCoroutineScope()
Button(onClick = { scope.launch { listState.animateScrollToItem(0) } }) { … }
```

Отличия от `LaunchedEffect`: не привязан к ключу; каждый клик может запустить **новую** задачу; но
все они отменяются вместе с композицией. → задачи **Л7, СЛ19**.

## 6. `rememberUpdatedState`: свежее значение без перезапуска

Проблема: долгий эффект `LaunchedEffect(Unit)` захватывает значение **на момент запуска** и не видит
его изменений (эффект-то не перезапускается). Добавить значение в ключ — эффект будет
**перезапускаться** на каждое изменение, что не нужно (хочется, чтобы таймер тикал, а колбэк был
всегда свежим).

`rememberUpdatedState(value)` держит **ссылку, обновляемую каждой рекомпозицией**, — долгий эффект
читает её и всегда видит последнее значение, НЕ перезапускаясь:

```kotlin
val currentOnTimeout by rememberUpdatedState(onTimeout)
LaunchedEffect(Unit) {              // запускается один раз
    delay(5_000)
    currentOnTimeout()             // вызовет САМЫЙ СВЕЖИЙ колбэк, а не тот, что был при старте
}
```

`rememberUpdatedState` разрывает связь «изменилось значение → перезапуск эффекта», сохраняя доступ к
свежему значению. → задачи **Л8, С14, СЛ17**.

## 7. Порядок применения при рекомпозиции

Когда кадр применяется, Compose обрабатывает эффекты через `RememberManager` в два прохода:
**сначала все `onDispose`/отмены** «забытых» и изменившихся эффектов, **затем все запуски** новых —
в порядке композиции. Это гарантирует, что очистка старого ресурса завершится до захвата нового.
→ задача **СЛ18**.

Неизменившиеся эффекты (ключ тот же) не трогаются вовсе — их корутины/подписки живут дальше.

## 8. Связь с другими темами

- **Тема 1 (рекомпозиция).** Эффект перезапускается по своим ключам, а не «на каждую рекомпозицию» —
  как skipping для UI, только для побочных эффектов. Ключ эффекта играет роль, аналогичную
  `remember(key)` из темы 2.
- **Тема 2 (состояние).** `rememberUpdatedState` — это `remember { mutableStateOf(value) }`, чьё
  значение переприсваивается каждой композицией; эффект читает его как обычный `State`.
- **Корутины.** `LaunchedEffect`/`rememberCoroutineScope` дают структурированную отмену: scope
  привязан к жизни композиции, поэтому «уехавший» экран не оставляет висящих корутин.
