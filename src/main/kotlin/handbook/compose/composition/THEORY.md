# Тема 5. Slot table и композиция (позиционная мемоизация, `key()`, movable content)

> Где Compose ХРАНИТ всё, что «запомнил» (`remember`, состояние, узлы дерева)? В **slot table** —
> плоской структуре, индексируемой по ПОЗИЦИИ вызова в дереве композиции. Отсюда фундаментальное
> свойство: идентичность composable — это его **место** в дереве, а не его данные. Для статичного UI
> это незаметно и идеально, но для списков рождает главную ловушку Compose: без `key()` состояние
> привязано к индексу, и любое переупорядочивание/вставка «перепутывает» его между элементами.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.composition.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику моделируем детерминированно на JVM: элемент [`Item`](Model.kt) (id + слот-состояние) и
> списки id. Идеи 1:1 переносятся на `androidx.compose.runtime` (slot table, `key`, `movableContentOf`).

## 1. Slot table: память композиции

Композиция — это дерево вызовов `@Composable`. Всё, что нужно запомнить между рекомпозициями
(значения `remember`, объекты состояния, ссылки на узлы UI-дерева), Compose складывает в **slot
table** — компактный линейный буфер «слотов», сгруппированный по структуре вызовов (**groups**:
restart-группы, replaceable-группы). При рекомпозиции рантайм идёт по slot table параллельно с
исполнением composable и **сопоставляет** новые вызовы со старыми слотами.

Ключевая идея: слот находится по **позиции** в дереве вызовов, а не по имени переменной или данным.

## 2. Позиционная мемоизация (positional memoization)

`remember { }` кэширует по МЕСТУ вызова. Два вызова `remember` в разных местах — разные слоты; один и
тот же вызов на той же позиции при рекомпозиции — тот же слот.

```kotlin
@Composable fun Screen() {
    val a = remember { computeA() }   // слот #1 (позиция 1)
    val b = remember { computeB() }   // слот #2 (позиция 2)
}
```

Даже условная структура сохраняет позиционную идентичность через **replaceable groups**: рантайм
знает, какой блок сейчас активен, и держит для каждой ветки свои слоты. Для статичного дерева
«идентичность = позиция» работает безупречно. → задачи **Л1, Л3, Л4**.

## 3. Проблема списков: идентичность = индекс

В цикле у элементов нет собственной позиционной идентичности, кроме **порядкового номера**:

```kotlin
Column {
    items.forEach { item ->
        var expanded by remember { mutableStateOf(false) }   // слот привязан к ИНДЕКСУ item
        Row(item, expanded) { expanded = !expanded }
    }
}
```

Пока список стабилен — ок. Но если элементы **переупорядочить, вставить или удалить**, позиции
«съедут», и слот с `remember`-состоянием окажется у другого элемента:

```
старое: [a→1, b→2, c→3]          (id → слот-состояние)
reorder: [c, a, b]
без key: позиция 0 (была a) теперь показывает c, но состояние слота #0 = 1  → c ПОКАЗЫВАЕТ состояние a
```

Так «раскрытая» карточка после сортировки оказывается раскрыта не у того элемента, введённый текст
прыгает на соседа и т.п. → задачи **С9, С11, С13, СЛ18**.

## 4. `key()`: стабильная идентичность

`key(id) { }` присваивает содержимому идентичность, не зависящую от позиции. Рантайм различает
элементы по `id`, а не по индексу, — и корректно **переносит** слоты при переупорядочивании,
**создаёт** для новых, **освобождает** для удалённых:

```kotlin
items.forEach { item ->
    key(item.id) {                       // стабильная идентичность
        var expanded by remember { mutableStateOf(false) }
        Row(item, expanded) { expanded = !expanded }
    }
}
// в LazyColumn: items(list, key = { it.id }) { … }
```

С ключами состояние **следует за элементом** при любой перестановке. → задачи **Л2, Л5–Л7, С10, С15, СЛ16, СЛ17, СЛ18**.

Правила ключей:
- **уникальность среди соседей.** Дубликаты ключей в одной области — баг (идентичности сталкиваются,
  поведение неопределённое/краш). → задачи **Л8, С12**.
- **уникальность нужна лишь среди соседей.** Один и тот же `key` в разных группах/местах — это разные
  идентичности (составная идентичность = позиция группы + ключ). → задача **СЛ20**.

## 5. Диф с ключами: переиспользовать, добавить, удалить, перенести

При рекомпозиции списка с ключами Compose диффит старый и новый наборы id и раскладывает элементы на:
- **переиспользованные** (id есть в обоих) — слот сохраняется;
- **добавленные** (только в новом) — новый слот;
- **удалённые** (только в старом) — слот освобождается;
- **перенесённые** — id остался, но сменил позицию: слот **двигают**, а не пересоздают.

→ задачи **СЛ16 (диф), СЛ17 (карта переиспользования слотов), С15 (перенос)**.

Практический эффект вставки в начало: без ключей «сдвигается» весь хвост (все позиции получают
другой элемент → переиспользование рушится), с ключами новый — только вставленный. → задача **С14**.

## 6. `movableContentOf`: перенести поддерево, сохранив состояние

`key()` спасает внутри одного списка. Но иногда composable нужно **переместить в другое место
дерева** — например, из вертикальной раскладки в горизонтальную, из одного контейнера в другой.
Обычно перемещение = уничтожение на старом месте + создание на новом (состояние теряется).

`movableContentOf { }` / `movableContentWithReceiverOf { }` делают контент **переносимым**: при
смене места его слоты (и всё состояние) **переезжают** вместе с ним:

```kotlin
val movablePlayer = remember { movableContentOf { VideoPlayer(state) } }

if (isLandscape) Row { movablePlayer() }      // тот же плеер,
else            Column { movablePlayer() }    // состояние (позиция видео!) сохраняется при повороте
```

Без movableContent тот же вызов в двух ветках — это два РАЗНЫХ поддерева по позиции, и переключение
пересоздаёт всё заново. → задача **СЛ19**.

## 7. Связь с другими темами

- **Тема 1 (рекомпозиция).** Slot table — то, по чему рантайм сопоставляет вызовы при рекомпозиции;
  скипы и восстановление читаемых состояний работают через неё.
- **Тема 2 (состояние).** `remember` — это чтение/запись слота в slot table по позиции; вся
  позиционная мемоизация — механизм под `remember`. `key()` меняет позиционную идентичность remember.
- **Тема 10 (списки).** `LazyColumn`/`items(key = …)` — прямое применение ключей плюс переиспользование
  и `contentType`; эта тема — фундамент под неё.
