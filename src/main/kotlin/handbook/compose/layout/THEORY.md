# Тема 6. Измерение и раскладка (`Constraints`, single-pass, intrinsics, `Layout`)

> Композиция (темы 1–5) строит дерево того, ЧТО показать. Раскладка отвечает на вопрос, КАКОГО
> размера и ГДЕ. В Compose это происходит за **один проход**: родитель спускает ребёнку
> `Constraints`, ребёнок измеряется **ровно один раз** и возвращает размер, родитель считает свой
> размер и расставляет детей. Понимание этого протокола объясняет, почему `fillMaxSize` внутри
> скролла падает, чем `size` отличается от `requiredSize`, и почему intrinsics «дорогие».
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.layout.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику моделируем детерминированно на JVM: [`Constraints`](Model.kt) и [`Size`](Model.kt). Идеи
> 1:1 переносятся на `androidx.compose.ui.layout`.

## 1. Три фазы кадра и место раскладки

Compose рисует кадр в три фазы: **Composition** (что) → **Layout** (размер и позиция) → **Drawing**
(пиксели). Эта тема — про среднюю фазу (фазы целиком — тема 8). Layout сама делится на два шага:
**measure** (сверху вниз: узнать размеры) и **place** (снизу вверх: расставить детей по координатам).

## 2. `Constraints`: язык договора о размере

Родитель передаёт каждому ребёнку [`Constraints`](Model.kt) — рамки `min..max` по ширине и высоте.
Ребёнок ОБЯЗАН выбрать размер в этих пределах:

```
Constraints(minWidth, maxWidth, minHeight, maxHeight)
выбранный размер = desired.coerceIn(min, max)   // всегда внутри рамок
```

→ задачи **Л1, Л2**.

Виды constraints:
- **loose** (`min == 0`) — «будь любым до max» (обычный `wrapContent`);
- **tight** (`min == max`) — точный размер навязан; → задача **Л6**;
- **bounded/unbounded** — `max` конечен или равен [`INFINITY`](Model.kt). Внутри скролла ось
  прокрутки **не ограничена** (`maxHeight == INFINITY`), поэтому `fillMaxHeight`/`fillMaxSize` там
  теряет смысл и падает — нечего «заполнять». → задача **Л7**.

## 3. Модификаторы размера через constraints

Модификаторы размера работают, **меняя constraints**:
- `fillMaxWidth()` → взять `maxWidth`. → задача **Л3**.
- `size(x)` → хотеть `x`, но результат всё равно **зажимается** во входящие constraints — родитель
  главнее. → задача **Л4**.
- `requiredSize(x)` → **игнорировать** входящие constraints и навязать `x` (ребёнок может вылезти за
  родителя). → задача **Л5**.
- `padding(p)` → **уменьшить** constraints, уходящие контенту (по оси на `2p`), а к своему размеру
  родитель потом прибавит паддинг обратно. → задача **Л8**.

Отсюда правило: `Modifier.size` не может «пробить» ограничения родителя, а `requiredSize` — может (и
потому опасен). → задачи **Л4, Л5**.

## 4. Single-pass измерение — перформанс-инвариант

Главное отличие от старой `View`-системы: там `measure` могли звать многократно (двойные проходы
`RelativeLayout`/вложенных `LinearLayout` с весами → экспоненциальный взрыв). В Compose **каждый
ребёнок измеряется ровно один раз** за проход раскладки. Это и делает раскладку предсказуемо быстрой.
→ задача **С14**.

Правило-следствие: **нельзя измерять ребёнка дважды** и нельзя читать собственный размер до
измерения детей. Обход, когда правда нужно «посмотреть заранее», — intrinsics (п. 6) или
`SubcomposeLayout`, и оба стоят дополнительной работы.

## 5. Измерение контейнеров: размер и расстановка

Контейнер измеряет детей, потом по их размерам считает свой и расставляет:

| Контейнер | Ширина | Высота | Расстановка |
|-----------|--------|--------|-------------|
| `Column`  | max ширин детей | сумма высот | стек по Y (бегущая сумма) |
| `Row`     | сумма ширин | max высот | стек по X |
| `Box`     | max ширин | max высот | по alignment (наложение) |

Свой итоговый размер контейнер тоже **зажимает во входящие constraints**. → задачи **С9–С13, СЛ16**.

`Row`/`Column` спускают детям constraints в зависимости от модификаторов: заполняющий ребёнок
получает tight-ширину (`min == max`), обычный — loose (`min == 0`). → задача **С15**.

Порядок в measure policy: сначала `measure` всех детей (получить [`Size`]), затем `layout(w, h) {
placeRelative(...) }` — расставить. → задача **СЛ16**.

## 6. Intrinsics: «спросить размер заранее»

Иногда родителю нужно узнать «естественный» размер ребёнка ДО обычного измерения — например, чтобы
`Divider` в `Row` был высотой с самого высокого соседа:

```kotlin
Row(Modifier.height(IntrinsicSize.Min)) {
    Text("Левый")
    Divider(Modifier.fillMaxHeight().width(1.dp))   // высота = высоте самого высокого текста
    Text("Правый\nв две строки")
}
```

Родитель запрашивает `minIntrinsicHeight` у детей и навязывает всем МАКСИМУМ. → задача **СЛ17**.

**Цена.** Intrinsic-запрос — это отдельный проход измерения поверх обычного, поэтому детей меряют
как бы дважды. На горячих путях (элементы списка) intrinsics лучше избегать. → задача **СЛ18**.

## 7. `Layout` и `weight`

Кастомную раскладку пишут через `Layout(content) { measurables, constraints -> … }` (или
`Modifier.layout`): измерить `measurables` в `Placeable`, вычислить размер, вернуть `layout(w, h) {
placeables.forEach { it.placeRelative(x, y) } }`. Это ровно то, что делают `Row`/`Column` внутри.

`Modifier.weight` в `Row`/`Column` распределяет **оставшееся** место пропорционально весам (после
измерения невзвешенных детей). → задача **СЛ19**.

Фаза placement — это чистая расстановка по координатам (без повторного измерения); например,
`Alignment.Center` кладёт ребёнка в `((cw - w) / 2, (ch - h) / 2)`. → задача **СЛ20**.

## 8. Связь с другими темами

- **Тема 5 (композиция).** Measure policy работает над узлами, которые composition разместила в
  дереве; `Layout` эмитит LayoutNode в тот же slot table.
- **Тема 7 (модификаторы).** Модификаторы размера/паддинга — это узлы цепочки, которые
  ПРЕОБРАЗУЮТ constraints вниз и размеры вверх; порядок в цепочке критичен (следующая тема).
- **Тема 8 (фазы).** Measure/place — средняя фаза; чтение состояния прямо в measure/place (deferred
  read) позволяет обновлять раскладку без рекомпозиции.
