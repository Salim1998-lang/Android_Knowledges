# Тема 3. Snapshot-система (изоляция, атомарность, конфликты и слияние)

> Под `mutableStateOf` (тема 2) и read tracking (тема 1) лежит **snapshot-система** — механизм, что
> делает состояние Compose одновременно **наблюдаемым**, **изолированным** и **потокобезопасным**.
> Именно она позволяет читать консистентный «слепок» состояния, менять его из фонового потока и
> **атомарно** публиковать изменения, а при гонке — обнаруживать конфликт и (иногда) сливать. Это
> самая «системная» тема модуля: понимаешь её — понимаешь, почему Compose-состояние ведёт себя как
> маленькая БД с MVCC.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.snapshot.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику моделируем детерминированно на JVM: версионированная запись [`Record`](Model.kt) и
> результат применения [`ApplyResult`](Model.kt). Идеи 1:1 переносятся на `androidx.compose.runtime.snapshots`.

## 1. Что такое snapshot

**Snapshot** — это изолированный, консистентный слепок всех наблюдаемых состояний в некоторый момент.
Аналогия — **транзакция БД с MVCC** (multiversion concurrency control):

- каждый снапшот видит согласованный набор значений (никаких «полуобновлённых» данных);
- разные снапшоты одновременно могут видеть **разные** значения одного и того же `State`;
- изменения в снапшоте изолированы, пока он не применён (`apply`).

Виды:
- **read-only** (`Snapshot.takeSnapshot()`) — только читает застывший слепок;
- **mutable** (`Snapshot.takeMutableSnapshot()`) — можно писать; изменения видны только внутри, пока
  не вызовешь `apply()`;
- **global** — снапшот по умолчанию, в котором работает большинство кода.

Compose берёт read-only снапшот на время композиции — поэтому кадр рисуется из **консистентного**
состояния, даже если фон в этот момент что-то меняет.

## 2. MVCC: состояние — это цепочка версий

`MutableState` хранит не одно значение, а **историю записей** ([`Record`](Model.kt)): «версия →
значение». Версия — это номер снапшота, сделавшего запись. Глобальная версия монотонно растёт с
каждым `apply`.

Чтение из снапшота версии `V` возвращает запись с **наибольшей версией `≤ V`** (и не принадлежащую
отменённому снапшоту):

```
history:  v1="a"   v3="c"   v5="e"
чтение на версии 4 → "c"   (v3 — наибольшая ≤ 4)
чтение на версии 5 → "e"
чтение на версии 0 → нет записи → default
```

→ задачи **Л1, Л2, Л3, СЛ19**.

## 3. Read isolation: снапшот «застыл» на своей версии

Снапшот, взятый на версии `base`, **не видит** записей, сделанных позже (`version > base`), — даже
если глобально их уже применили. Он живёт в своём застывшем мире:

- запись видна снапшоту ⇔ `writeVersion <= base`; → задача **Л5**.
- всё, что новее, — скрыто; → задача **Л6**.
- поэтому **несколько чтений подряд внутри одного снапшота дают одно и то же** значение, даже если
  параллельно кто-то меняет состояние. Расчёты консистентны. → задача **СЛ18**.

При этом снапшот видит **свои собственные** ещё не применённые записи (write в mutable-снапшоте сразу
виден его читателям, но никому снаружи). → задачи **Л7, С9**.

## 4. `apply()`: атомарная публикация

`mutableSnapshot.apply()` публикует все записи снапшота в глобальное состояние **атомарно** — «всё
или ничего». Другие никогда не увидят половину изменений: либо весь набор, либо ничего. Успешный
`apply` продвигает глобальную версию на 1, и записи получают новый номер. → задачи **Л8, С14, СЛ16**.

Удобная обёртка «взять → выполнить → применить»:

```kotlin
Snapshot.withMutableSnapshot {
    account.balance -= 100      // изменения изолированы,
    savings.balance += 100      // применятся атомарно и вместе
}
```

Так делают согласованное изменение НЕСКОЛЬКИХ состояний: снаружи баланс не «мигнёт» промежуточным
несогласованным значением. → задача **СЛ16**.

## 5. Конфликты: когда два снапшота столкнулись

Пока снапшот открыт, глобальное состояние могло уйти вперёд (кто-то другой применил свои записи).
При `apply` система сравнивает: **пересекаются ли состояния, что записал наш снапшот, с теми, что
изменились глобально с момента его взятия**. Если да — **конфликт**. → задачи **С10, С11**.

```
глобально:  count = 0
A: takeMutableSnapshot()   B: takeMutableSnapshot()   (оба видят 0)
A: count = 5;  A.apply()   → глобально count = 5
B: count = 8;  B.apply()   → КОНФЛИКТ (count изменился под B)
```

## 6. Слияние (merge policy) или провал

Что делать с конфликтом, решает **политика состояния** — `SnapshotMutationPolicy.merge(previous,
current, applied)`, где `previous` — значение на общей базе, `current` — уже в глобальном, `applied`
— что хочет записать наш снапшот. Она возвращает слитое значение **или null** (неразрешимо):

- **менялась только наша сторона** (`current == previous`) → берём `applied`;
- **менялась только чужая** (`applied == previous`) → берём `current`;
- **обе пришли к одному** (`applied == current`) → без разницы;
- **иначе** → `null` = настоящий конфликт.

→ задачи **С12, СЛ20**.

По умолчанию (`structuralEqualityPolicy`, `referentialEqualityPolicy`) merge **всегда возвращает
null** — то есть обычное `mutableStateOf` при конфликте `apply` **проваливается**
([`ApplyResult.FAILURE`](Model.kt)), и запись отбрасывается целиком (атомарно). Специальные политики
(или `SnapshotStateList`/`SnapshotStateMap`) умеют сливать непересекающиеся изменения
([`ApplyResult.MERGED`](Model.kt)). → задачи **С13, СЛ17**.

На практике конфликты редки: почти весь код работает в глобальном снапшоте на главном потоке.
Конфликт возможен, когда состояние правят **параллельно** (фон + UI) — и тогда snapshot-система
честно об этом сообщает, а не молча теряет данные.

## 7. `snapshotFlow`: состояние как поток

`snapshotFlow { block }` наблюдает за состоянием, прочитанным в `block`, и эмитит новое значение при
его изменении — с `distinctUntilChanged` (первое значение + только реальные смены). Мост из
snapshot-мира в корутины/`Flow`:

```kotlin
snapshotFlow { listState.firstVisibleItemIndex }
    .distinctUntilChanged()
    .collect { index -> analytics.log(index) }
```

→ задача **С15**.

## 8. Связь с темами 1–2

- **Тема 1 (рекомпозиция).** Read tracking реализован через снапшоты: рантайм регистрирует, какие
  `State` прочитал scope, и подписывается на их изменения в snapshot-системе (apply-observer).
- **Тема 2 (состояние).** `mutableStateOf` — это `SnapshotMutableState` поверх [`Record`]-цепочки;
  его политика равенства и есть та самая merge policy. `mutableStateListOf`/`mutableStateMapOf`
  умеют сливаться, а обычный `State` — нет.
- Изоляция снапшота — причина, почему во время композиции значения не «плывут»: кадр строится из
  застывшего слепка.
