# Тема 2. Состояние (`remember`, `mutableStateOf`, `rememberSaveable`, `derivedStateOf`, hoisting)

> Рекомпозиция (тема 1) отвечает на вопрос «что перерисовать», а **состояние** — на вопрос «что
> запомнить между перерисовками». Composable-функция вызывается много раз и в непредсказуемом
> порядке; её локальные `val`/`var` живут только один вызов. Чтобы значение пережило рекомпозицию,
> его кладут в `remember`; чтобы UI реагировал на изменения — в `mutableStateOf`; чтобы пережить
> поворот экрана — в `rememberSaveable`. А куда именно поместить состояние в дереве — решает
> **state hoisting**.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.compose.state.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику моделируем детерминированно на JVM (слот [`Slot`](Model.kt), события [`SurvivalEvent`](Model.kt),
> дерево через parent-map) — без Compose-рантайма и Android. Идеи 1:1 переносятся на настоящий
> `androidx.compose.runtime`.

## 1. Почему обычная переменная не работает

Composable вызывается заново на каждой рекомпозиции. Локальная переменная пересоздаётся каждый раз:

```kotlin
@Composable
fun Counter() {
    var count = 0          // ← сбрасывается в 0 на КАЖДОЙ рекомпозиции
    Button(onClick = { count++ }) { Text("$count") }  // всегда 0
}
```

Нужны два разных механизма, которые часто путают:
- **`remember`** — «запомни это значение между рекомпозициями» (кэш по позиции вызова);
- **`mutableStateOf`** — «сделай это значение НАБЛЮДАЕМЫМ» (чтение регистрируется, запись
  инвалидирует читателей — см. тему 1).

Они ортогональны и обычно нужны вместе.

## 2. `remember`: кэш по позиции в slot table

`remember { compute() }` при первой композиции выполняет лямбду и сохраняет результат в slot table
по **позиции вызова**; при рекомпозиции возвращает сохранённое, **не вызывая лямбду снова**.

```kotlin
val expensive = remember { computeExpensiveThing() }  // посчитается один раз
```

Это чистый кэш «на время жизни композиции в этом месте дерева». → задачи **Л2, Л8, С9**.

## 3. `mutableStateOf` + `remember`: наблюдаемое и живущее состояние

`mutableStateOf(x)` создаёт наблюдаемый `MutableState`. Но сам объект состояния тоже нужно **запомнить**,
иначе он пересоздастся на следующей рекомпозиции — и все записи потеряются:

```kotlin
var count by remember { mutableStateOf(0) }   // ✅ переживает рекомпозицию
// var count by mutableStateOf(0)             // ❌ пересоздаётся → count всегда сбрасывается
```

Правило: **`mutableStateOf` почти всегда оборачивают в `remember`**. Забыть `remember` — классический
баг «значение сбрасывается». → задача **Л3**.

## 4. `remember(key)`: сброс кэша при изменении входа

`remember(key1, key2) { compute() }` переиспользует значение, пока **все ключи структурно не
изменились**. Как только ключ сменился — кэш сбрасывается и лямбда считается заново:

```kotlin
val scaled = remember(user.id) { loadAvatar(user.id) }  // пересчёт при смене user.id
```

Ключи — способ сказать «пересобери это, когда изменилось вот это». → задачи **Л1, Л8, С9**.

Ловушка: если в ключ передать значение, которое **меняется на каждой рекомпозиции** (новый объект,
незапомненная лямбда), кэш сбрасывается всегда — `remember` не даёт ничего. → задача **С15**.

## 5. `rememberSaveable`: пережить поворот и смерть процесса

`remember` живёт, пока композиция на месте. Он НЕ переживает:
- **смену конфигурации** (поворот, смена языка/темы) — Activity и композиция пересоздаются;
- **смерть процесса** — система убила приложение в фоне и восстанавливает экран.

`rememberSaveable` дополнительно кладёт значение в `Bundle` savedInstanceState и восстанавливает его
после этих событий:

```kotlin
var text by rememberSaveable { mutableStateOf("") }  // переживёт поворот
```

| Событие | `remember` | `rememberSaveable` |
|---------|:---:|:---:|
| рекомпозиция | ✅ | ✅ |
| смена конфигурации (поворот) | ❌ | ✅ |
| смерть процесса | ❌ | ✅ |

→ задачи **Л4, Л5, СЛ16, СЛ17**.

**Что можно сохранять.** В `Bundle` автоматически кладутся примитивы, `String`, `Parcelable` и т.п.
Свой доменный тип нужно сопроводить `Saver` (`listSaver`/`mapSaver`/кастом), иначе рантайм упадёт.
→ задача **Л6**.

```kotlin
val state = rememberSaveable(stateSaver = MyTypeSaver) { mutableStateOf(MyType()) }
```

## 6. `derivedStateOf`: считать из состояния и гасить шум

Когда одно состояние **вычисляется** из другого, а входное меняется ЧАСТО, но выходное — редко,
прямое чтение вызывает лавину лишних рекомпозиций. `derivedStateOf` пересчитывает производное при
изменении входа, но **будит читателей только если поменялся РЕЗУЛЬТАТ**:

```kotlin
val showButton by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}
```

`firstVisibleItemIndex` меняется на каждый элемент при скролле, но `> 0` — лишь один раз. Без derived
кнопка рекомпозировалась бы постоянно; с derived — дважды за всю прокрутку. → задачи **Л7, С10, С11, СЛ18**.

Отличие от `remember(key)`: `remember(key)` пересчитывает по **явному** списку ключей; `derivedStateOf`
сам отслеживает, какие `State` прочитал внутри, и сравнивает **результат**. Используй derived, когда
результат — функция от другого наблюдаемого состояния. → сравнение в задаче **С11**.

## 7. State hoisting: единый источник истины

**State hoisting** — вынос состояния из composable вверх, к вызывающему. Composable становится
**stateless**: не держит своего состояния, а принимает **текущее значение + колбэк изменения**
(паттерн `value` + `onValueChange`):

```kotlin
// stateful (держит состояние сам):
@Composable fun NameField() { var name by remember { mutableStateOf("") }; TextField(name, { name = it }) }

// stateless (состояние поднято — переиспользуемо и тестируемо):
@Composable fun NameField(value: String, onValueChange: (String) -> Unit) { TextField(value, onValueChange) }
```

Зачем: **single source of truth** (одно значение, а не копии в разных местах), переиспользуемость,
тестируемость, управляемость сверху. → задача **С14**.

Куда поднимать: к **самому низкому общему предку** (LCA) всех, кто состоянием пользуется — не выше и
не ниже:
- **ниже LCA** — часть пользователей его не увидит;
- **выше LCA** (over-hoisting) — рекомпозиция затрагивает лишнее поддерево, и растёт **prop drilling**
  (значение приходится «прокидывать» через много промежуточных слоёв).

→ задачи **С12, С13, СЛ19, СЛ20**.

Когда prop drilling становится болезненным, состояние выносят в отдельный **state holder** (обычный
класс или `ViewModel`), а не поднимают всё выше и выше.

## 8. Как это связано с рекомпозицией (тема 1)

- `mutableStateOf` — тот самый наблюдаемый `State`, чьё чтение регистрируется, а запись инвалидирует
  читателей (тема 1, п. 2–3).
- Где живёт состояние (hoist target) — определяет, какой **recomposition scope** инвалидируется:
  чем выше поднято, тем шире scope и тем больше рекомпозируется. Over-hoisting — прямой источник
  лишних рекомпозиций из темы 1.
- `derivedStateOf` — инструмент из темы 1 (гашение шума), рассмотренный здесь как API состояния.
