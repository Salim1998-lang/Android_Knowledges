# Тема 10. Тестирование корутин

Все прошлые темы **прогонялись** через `runTest { }` — не объясняя, что это. Здесь разбираемся, как
тестировать корутины: почему `delay(1000)` в тесте не ждёт секунду, кто такой `TestDispatcher` и как
управлять виртуальным временем.

## 1. Проблема: время и недетерминизм

Наивный тест корутины плох по двум причинам:
- **Реальные задержки.** `delay(10_000)` в коде → тест реально ждёт 10 секунд. Сотня таких — и сборка
  ползёт.
- **Недетерминизм.** Настоящие потоки планируются как попало → тест то зелёный, то красный (flaky).

Решение — **виртуальное время** и **тестовый диспетчер**: задержки не ждут по-настоящему, а
«проматываются», и всё исполняется на одном управляемом потоке.

## 2. `runTest { }` — точка входа

`runTest` запускает тело теста в `TestScope` с виртуальным временем. `delay` внутри **не ждёт
реально** — планировщик проматывает время автоматически, когда все корутины ждут:

```kotlin
@Test fun example() = runTest {          // это TestScope
    val t0 = currentTime                 // виртуальные часы, старт = 0
    delay(1000)                          // мгновенно по реальному времени
    assertEquals(1000, currentTime - t0) // но виртуально прошло 1000 мс
}
```

- `runTest` **сам проматывает** время, пока есть отложенная работа, и ждёт завершения всех корутин,
  запущенных в его scope (структурная конкурентность).
- Возвращать нужно результат `runTest(...)` из тест-метода (`= runTest { ... }`).

## 3. `currentTime` и виртуальные часы

`currentTime` (свойство `TestScope`) — текущее виртуальное время в миллисекундах. Последовательные
`delay` **складываются**, а конкурентные (в разных корутинах) идут **параллельно** — итоговое время
равно максимуму, а не сумме:

```kotlin
delay(100); delay(200)                                  // currentTime += 300 (последовательно)

coroutineScope { launch { delay(100) }; launch { delay(200) } }  // currentTime += 200 (параллельно)
```

## 4. Ручное управление временем

Когда работа **запущена** (`launch`/`async`), но ты хочешь контролировать её пошагово:

| Инструмент | Что делает |
|-----------|-----------|
| `runCurrent()` | выполнить задачи, запланированные на **текущий** момент (без проматывания времени) |
| `advanceTimeBy(ms)` | продвинуть часы на `ms`, выполняя всё, что запланировано **строго раньше** новой отметки |
| `advanceUntilIdle()` | проматывать, пока не выполнится **вся** отложенная работа |

> ⚠️ **Гранична­я тонкость `advanceTimeBy`.** Задача, запланированная **ровно** на `now + ms`, НЕ
> выполнится (интервал полуоткрытый). Чтобы «дожать» её, добавь `runCurrent()` после, либо
> продвигай на чуть больше.

## 5. `TestDispatcher`: ленивый vs жадный

Тестовые диспетчеры делят общий `testScheduler` (поэтому виртуальное время у них общее):

| Диспетчер | Поведение | Когда |
|-----------|-----------|-------|
| `StandardTestDispatcher` | **ленивый**: `launch` не исполняется, пока не промотаешь время (`runCurrent`/`advance*`) | по умолчанию в `runTest`; полный контроль порядка |
| `UnconfinedTestDispatcher` | **жадный**: `launch` исполняется сразу до первой приостановки | когда хочется «просто чтобы запустилось» без ручного проматывания |

```kotlin
val d = StandardTestDispatcher(testScheduler)
var ran = false
launch(d) { ran = true }
// ran == false — ещё не исполнилось
runCurrent()
// ran == true
```

## 6. `backgroundScope` — для бесконечных корутин

`runTest` ждёт завершения всех корутин своего scope. Но коллектор `StateFlow` или бесконечный
тикер **никогда не завершатся** → тест повиснет. Их запускают в `backgroundScope`: он живёт во время
теста и **автоматически отменяется** в конце.

```kotlin
val state = MutableStateFlow(0)
backgroundScope.launch {                 // не блокирует завершение runTest
    state.collect { /* ... */ }
}
state.value = 1
runCurrent()
```

## 7. Тестирование таймаутов

`withTimeout`/`withTimeoutOrNull` работают на виртуальном времени — тайм-аут «срабатывает» мгновенно:

```kotlin
val result = withTimeoutOrNull(1000) { delay(2000); "done" }
assertNull(result)              // тайм-аут, но тест не ждал ни секунды
```

## 8. Подмена `Dispatchers.Main`: `setMain` / `resetMain`

В чистой JVM нет `Dispatchers.Main` (это UI-поток Android/Swing). Если код использует `Main`, в тесте
его подменяют тестовым диспетчером:

```kotlin
@BeforeEach fun setUp()   { Dispatchers.setMain(StandardTestDispatcher()) }
@AfterEach  fun tearDown(){ Dispatchers.resetMain() }
```

Так `withContext(Dispatchers.Main) { }` в продакшн-коде работает и под тестом.

## 9. `runTest` и реальные диспетчеры

Если внутри теста код уходит на `Dispatchers.IO`/`Default` (реальные потоки), виртуальное время там
**не действует** — эти участки выполняются по-настоящему, а `runTest` дожидается их. Для полного
контроля виртуальным временем **внедряй диспетчер** (передавай его параметром), а в тесте подставляй
тестовый — это главный приём тестируемости.

## 10. Чек-лист

- Тест корутин → `@Test fun x() = runTest { }`.
- Задержки не ждут реально; `currentTime` — виртуальные часы.
- `launch` на `StandardTestDispatcher` ленив → продвинь время (`runCurrent`/`advanceUntilIdle`).
- Бесконечные корутины → `backgroundScope`.
- Код использует `Main` → `setMain`/`resetMain`.
- Хочешь контроль над потоком в коде → **внедряй диспетчер**, не хардкодь.
