# Тема 5. Диспетчеры и `CoroutineContext`

Предыдущие темы **пользовались** `withContext(Dispatchers.IO)` как данностью. Здесь разбираемся,
что это на самом деле: из чего состоит контекст корутины, кто и на каком потоке её исполняет и как
этим осознанно управлять.

## 1. `CoroutineContext` — «паспорт» корутины

Каждая корутина несёт **контекст** — неизменяемый набор элементов, индексируемый по ключу. Главные
элементы:

| Элемент | За что отвечает | Ключ |
|---------|-----------------|------|
| `Job` | жизненный цикл, отмена, дерево родитель-дети | `Job` |
| `CoroutineDispatcher` | на каком потоке/пуле исполняться | `ContinuationInterceptor` |
| `CoroutineName` | имя для отладки/логов | `CoroutineName` |
| `CoroutineExceptionHandler` | «последний рубеж» для необработанных ошибок | `CoroutineExceptionHandler` |

Читать элементы можно прямо из `coroutineContext`:

```kotlin
suspend fun who() {
    println(coroutineContext[CoroutineName]?.name)          // имя, если задано
    val onDefault = coroutineContext[ContinuationInterceptor] === Dispatchers.Default
}
```

> 🧠 **Контекст — это `Map` от ключа к элементу.** `coroutineContext[Key]` достаёт элемент; `+`
> объединяет контексты; `minusKey(Key)` убирает элемент.

## 2. Диспетчеры — кто и где исполняет

**Диспетчер** решает, на каком потоке пойдёт корутина. Четыре штатных:

| Диспетчер | Для чего | Пул |
|-----------|----------|-----|
| `Dispatchers.Default` | **CPU-bound**: вычисления, парсинг, сортировка | потоков ≈ числу ядер (мин. 2) |
| `Dispatchers.IO` | **блокирующий IO**: сеть, диск, БД | до 64 потоков (шарит с Default) |
| `Dispatchers.Main` | **UI** (Android/Swing) | один UI-поток; в чистой JVM нет по умолчанию |
| `Dispatchers.Unconfined` | не переключает поток — стартует в вызывающем | — (спец-случаи/тесты) |

> 🧠 **Правило IO vs Default.** *Ждём* внешний ресурс (сеть/диск) — **IO** (поток всё равно простаивает
> в блокировке, потоков много). *Грузим процессор* — **Default** (потоков ровно под ядра, лишние
> только навредят). **Никогда не блокируй `Default`** тяжёлым IO — займёшь и без того скудный пул.

`Unconfined` в проде почти не нужен: он исполняет до первой приостановки на текущем потоке, а после —
на том, что возобновил корутину. Легко выстрелить в ногу.

## 3. `withContext` — переключение

`withContext(ctx) { }` **временно** меняет контекст (обычно — диспетчер), выполняет блок, возвращает
его результат и переключается обратно. Это `suspend`, ждёт завершения блока и его детей:

```kotlin
suspend fun loadUser(id: String): User = withContext(Dispatchers.IO) {
    api.fetchUser(id)          // блокирующий вызов — на IO
}                              // вернулись на исходный диспетчер с результатом
```

- `withContext` **не создаёт конкурентность** — это последовательный «сходи и вернись».
- Для параллельного запуска — `async`/`launch` (тема 2), для смены потока — `withContext`.

> ⚠️ **Не оборачивай в `withContext(Default)` единичный лёгкий вызов.** Переключение контекста стоит
> ресурсов; оно оправдано вокруг **ощутимой** работы, а не одной строки.

## 4. Наследование контекста

Дочерняя корутина **наследует** контекст родителя — кроме `Job` (у неё свой дочерний `Job`, привязанный
к родительскому). Поэтому `CoroutineName`, диспетчер и прочее «протекают» вниз, если не переопределить:

```kotlin
withContext(CoroutineName("loader")) {
    launch {                                   // без явного имени —
        println(coroutineContext[CoroutineName]?.name)   // "loader" (унаследовано)
    }
    launch(CoroutineName("worker")) {          // переопределили
        println(coroutineContext[CoroutineName]?.name)   // "worker"
    }
}
```

## 5. Комбинирование элементов через `+`

Контексты складываются оператором `+`. При конфликте ключей **побеждает правый** операнд:

```kotlin
val ctx = Dispatchers.IO + CoroutineName("sync")     // диспетчер + имя
launch(ctx) { /* на IO, с именем "sync" */ }

val merged = CoroutineName("a") + CoroutineName("b")  // → "b" (правый выигрывает)
```

## 6. `CoroutineName` — для отладки

Имя попадает в имя потока (при `-Dkotlinx.coroutines.debug`) и в дампы — резко упрощает чтение логов
конкурентного кода. Стоит почти ничего, помогает много:

```kotlin
launch(CoroutineName("prefetch-images")) { ... }
```

## 7. `limitedParallelism` — свой лимит параллелизма

`dispatcher.limitedParallelism(n)` даёт **представление** диспетчера, которое исполняет не больше `n`
корутин одновременно (поверх общего пула, без создания новых потоков). Так ограничивают нагрузку на
ресурс — например, не больше 4 одновременных запросов к API:

```kotlin
val apiDispatcher = Dispatchers.IO.limitedParallelism(4)
suspend fun fetchAll(ids: List<String>) = withContext(apiDispatcher) {
    ids.map { async { api.fetch(it) } }.awaitAll()   // максимум 4 запроса разом
}
```

Это современная замена самодельным `newFixedThreadPoolContext` — без утечки потоков.

## 8. `withContext` vs `launch`/`async`

| Нужно | Инструмент |
|-------|-----------|
| сменить поток для куска работы и **вернуть результат** | `withContext(dispatcher) { }` |
| запустить работу **параллельно**, получить результат позже | `async { }.await()` |
| запустить фоновую работу без результата | `launch { }` |

`withContext(d) { }` ≈ `async(d) { }.await()`, но дешевле и выразительнее, когда параллелизм не нужен.

## 9. Чтение и правка контекста

- `coroutineContext` — контекст текущей корутины (из любого `suspend`-кода).
- `currentCoroutineContext()` — то же явной функцией (полезно внутри `Flow`-строителей).
- `coroutineContext[Job]` — `Job` корутины; `isActive` — короткая форма `coroutineContext[Job]?.isActive`.
- `ctx.minusKey(CoroutineName)` — контекст без имени; `a + b` — объединение.

## 10. Частые ошибки

- **Блокирующий вызов на `Default`** (или на `Main`) — займёт скудный пул/заморозит UI. → `withContext(IO)`.
- **`Unconfined` в проде** — непредсказуемый поток после приостановки. → штатный диспетчер.
- **`withContext` ради конкурентности** — он последовательный. → `async`/`launch`.
- **Ручные `newSingleThreadContext`/пулы без закрытия** — утечка потоков. → `limitedParallelism`.
- **Слишком мелкое переключение** — `withContext` вокруг одной дешёвой операции дороже самой операции.
