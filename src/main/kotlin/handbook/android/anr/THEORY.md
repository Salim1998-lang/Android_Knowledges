# Тема 6. ANR, кадры и jank

> Всё предыдущее сходится здесь. Главный поток (тема 1) обязан успевать рисовать кадр за **бюджет**
> (~16 мс при 60 Гц) и обрабатывать ввод за секунды — иначе пользователь видит **рывки (jank)** или
> диалог **ANR** («приложение не отвечает»). Это то, за что бьют в Play Vitals и на код-ревью, и
> любимая тема senior-собеса про производительность.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt), прогоняя тесты:
> `./gradlew test --tests "handbook.android.anr.*"`. Застрял — [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Модели детерминированы ([`Model.kt`](Model.kt)): таймлайн кадров, пороги ANR, `Choreographer`-фазы,
> `StrictMode`-детектор — без реального рендера и эмулятора. Законы 1:1 переносятся на Android.

## 1. Бюджет кадра и refresh rate

Экран обновляется с частотой **refresh rate**. Каждое обновление (**vsync**) система просит
приложение отдать готовый кадр. Значит, весь UI-код одного кадра должен уложиться в **бюджет**:

```
бюджет кадра (мс) = 1000 / refreshRate
```

| Частота | Бюджет | Где |
|--------:|-------:|-----|
| 60 Гц | ~16.7 мс | базовый |
| 90 Гц | ~11.1 мс | многие флагманы |
| 120 Гц | ~8.3 мс | ProMotion/высокие |

→ задача **Л1**. Знаменитые «16 мс» — это 60 Гц. На 120 Гц бюджет **вдвое жёстче** — код, «летавший»
на 60 Гц, может джанкать на 120. Кадр **janky**, если работа превысила бюджет. → задачи **Л2, Л4**.

## 2. Как рождается jank: vsync и `Choreographer`

`Choreographer` — дирижёр кадра. По каждому сигналу vsync он на главном потоке выполняет фазы кадра
**строго по порядку**:

```
INPUT (ввод) → ANIMATION (аниматоры) → INSETS → TRAVERSAL (measure→layout→draw) → COMMIT
```

→ задача **С14**. Бюджет делится между ВСЕМИ фазами: если тяжёлый `onDraw` или пересчёт layout
съедает бюджет целиком — кадр не готов к следующему vsync, он **пропускается (dropped frame)**, на
экране повтор старого кадра — виден рывок. → задачи **С15, Л3**.

`Choreographer.postFrameCallback { frameTimeNanos -> }` даёт хук на каждый кадр (так делают
кастомные анимации и замер jank).

## 3. Каскад: один тяжёлый кадр валит соседей

Главный поток однопоточный (тема 1), поэтому **опоздавший кадр сдвигает последующие**. Кадр k может
начаться не раньше своего vsync И не раньше, чем закончится предыдущий:

```
start[k]   = max(k*budget, present[k-1])
present[k] = start[k] + work[k]
```

→ задача **С9**. Из-за этого джанк «размазывается»: наивный подсчёт «work > budget» (задача **Л4**)
недооценивает проблему — важнее, сколько кадров реально не успели к своему дедлайну с учётом каскада.
→ задача **С10**. Долгий кадр в 50 мс при бюджете 16 — это ~3 пропущенных кадра подряд. → задача **Л3**.

## 4. Метрики плавности

«Тормозит» — не метрика. Измеряют:
- **janky frames %** — доля кадров сверх бюджета (Play Vitals, `dumpsys gfxinfo`). → задача **Л5**.
- **перцентили времени кадра** — p50/p90/p95/p99 (Perfetto, Jetpack Macrobenchmark). p99 показывает
  «хвост» — редкие, но заметные тормоза. → задача **СЛ17**.
- **worst hitch** — максимальное превышение бюджета (самый долгий одиночный кадр). Один кадр в 700 мс
  субъективно хуже, чем много кадров по 20 мс. → задача **СЛ16**.
- **длина серии janky-кадров** — устойчивый фриз воспринимается куда хуже одиночного пропуска. → задача **СЛ19**.

Правило: гнаться не только за средним, но и за **хвостом** (p99, worst hitch, streak) — именно он
создаёт ощущение «залипает».

## 5. ANR: когда главный поток завис надолго

Если главный поток не обработал важное событие за отведённое время — система показывает **ANR**.
Пороги (приблизительно):

| Что «завис» | Порог |
|-------------|------:|
| диспетчеризация ввода | 5 с |
| `BroadcastReceiver` (foreground) | 10 с |
| `BroadcastReceiver` (background) | 60 с |
| `Service` (foreground) | 20 с |
| `Service` (background) | ~200 с |

→ задачи **Л6, Л7**. ANR — это буквально «цикл событий главного потока застрял слишком надолго» (см.
тему 1). Две типовые причины:
- **один длинный блок**: единственный обработчик держит поток дольше порога (сеть/диск/тяжёлый CPU на
  главном). → задача **СЛ18**.
- **длинный бэклог**: очередь работы на главном такая, что ввод, встав в хвост, ждёт дольше порога.
  Задержка ввода = `max(0, Σбэклог − момент_прихода)`. → задачи **С11, С12**.

Ещё причины ANR (для полноты): дедлок с блокировкой главного потока, синхронный `Binder`-вызов к
зависшему процессу (тема про Binder), слишком долгий `onCreate`/`onReceive`.

### Как система это ловит
Watchdog построен на той же механике сообщений: во `InputDispatcher`/`ActivityManager` ставится
таймер на доставку; не уложился — собирается **ANR-трейс** (`/data/anr/traces.txt`) со стеками всех
потоков. Читать эти трейсы — навык темы `handbook.android.diagnostics`.

## 6. Лечение: не блокируй главный поток

Всё сводится к одному правилу: **никакой блокирующей/тяжёлой работы на главном потоке**.
- Диск/сеть/БД/парсинг — на фоновые потоки, пулы (тема 3), корутины (`Dispatchers.IO`/`Default`),
  результат — обратно на главный (тема 2).
- Тяжёлый UI: упрощай иерархию `View`, избегай пересчётов layout, тяжёлого `onDraw`, больших bitmap
  на главном.
- Разбивай крупную работу и откладывай на `IdleHandler`/фон (тема 1).
- Никогда не `Thread.sleep`, `.get()`, `synchronized`-ожидание, синхронный I/O на главном.

## 7. `StrictMode`: ловим нарушения на этапе разработки

`StrictMode` — детектор «плохого на главном потоке». Настраивается в debug-сборках:

```kotlin
StrictMode.setThreadPolicy(
    StrictMode.ThreadPolicy.Builder()
        .detectDiskReads().detectDiskWrites().detectNetwork()
        .penaltyLog()            // или .penaltyDeath() — падать при нарушении
        .build()
)
StrictMode.setVmPolicy(          // утечки Activity/Closable и т.п. — тема про lifecycle/память
    StrictMode.VmPolicy.Builder().detectLeakedClosableObjects().penaltyLog().build()
)
```

- **ThreadPolicy** ловит на главном потоке **диск и сеть** (обычный CPU-код — не ловит). → задачи **Л8, С13**.
- **penaltyLog** пишет в лог, **penaltyDeath** роняет приложение — превращает «тихую» проблему в
  немедленный краш, чтобы поймать её на этапе разработки, а не в проде. → задача **СЛ20**.

`StrictMode` включают ТОЛЬКО в debug (в релизе penaltyDeath недопустим).
