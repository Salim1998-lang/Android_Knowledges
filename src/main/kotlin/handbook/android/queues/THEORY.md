# Тема 5. Producer-consumer и backpressure

> Пул (тема 3) и `HandlerThread` (тема 2) — это **потребители**. Но что делать, когда **продюсер
> быстрее потребителя**? Данные копятся. Либо тормозим продюсера (backpressure), либо теряем часть
> данных осознанно (throttle/debounce/конфляция), либо — при наивном подходе — растёт очередь и
> прилетает **OOM**. Это ежедневная сеньор-задача: сенсоры, скролл, поиск-по-мере-ввода, real-time
> обновления, логи, аналитика.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt), прогоняя тесты:
> `./gradlew test --tests "handbook.android.queues.*"`. Застрял — [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Механику `BlockingQueue` отрабатываем на НАСТОЯЩИХ потоках; стратегии backpressure — как чистые
> функции над потоком [`Event`](Model.kt) (значение + время), чтобы проверять их детерминированно.

## 1. Проблема: продюсер быстрее потребителя

Пусть продюсер эмитит 1000 событий/с, а потребитель успевает 100/с. За секунду копится 900
необработанных. Варианты:
1. **Тормозить продюсера** — блокировать его, пока потребитель не разгребёт (lossless backpressure).
2. **Терять данные осознанно** — throttle, debounce, sample, конфляция, drop-oldest/latest.
3. **Батчить** — обрабатывать пачками, повышая пропускную способность.
4. **Ничего не делать** — очередь растёт без предела → задержка растёт → **OOM**. Так делать нельзя.

Выбор между (1) и (2) — фундаментальный компромисс: **потери против задержки/памяти**. Нельзя иметь
и «без потерь», и «без роста очереди», и «быстрый продюсер» одновременно.

## 2. `BlockingQueue`: несущая конструкция

`java.util.concurrent.BlockingQueue` — потокобезопасная очередь с блокирующими операциями. Основа
любого producer-consumer:

| Операция | Полная очередь | Пустая очередь |
|----------|----------------|----------------|
| `put(x)` / `take()` | **блокирует** | **блокирует** |
| `offer(x)` / `poll()` | вернёт `false` | вернёт `null` |
| `offer(x, t, unit)` / `poll(t, unit)` | ждёт до `t`, потом `false` | ждёт до `t`, потом `null` |
| `drainTo(coll)` | — | забирает всё разом |

→ задачи **Л1** (`offer` не блокирует), **Л2** (`poll`→null), **Л3** (`drainTo`), **Л6** (`offer` с таймаутом).

Реализации:
- **`ArrayBlockingQueue(cap)`** — ограниченная (массив). Твой главный инструмент backpressure.
- **`LinkedBlockingQueue()`** — по умолчанию **безграничная** (⚠️ тот же риск OOM, что в теме 3 с пулом).
- **`SynchronousQueue`** — ёмкость 0: `put` ждёт `take` (прямая передача из рук в руки). → задача **Л7**.
- **`PriorityBlockingQueue`** — по приоритету. **`DelayQueue`** — по времени готовности.

### Классический producer-consumer + poison pill
Потребитель на своём потоке крутит `while(true){ take() }`. Как его остановить? Положить в очередь
**«ядовитую пилюлю»** (сентинел) — потребитель, увидев её, выходит. → задача **Л4**. На N
потребителей кладут N пилюль. → задача **С9** (fan-out).

## 3. Ограниченная очередь = честный backpressure

Главная идея: **ограниченная очередь с блокирующим `put` тормозит продюсера сама**. Когда буфер
полон, `put` блокируется — продюсер физически не может бежать быстрее потребителя. Ничего не
теряется, порядок сохраняется, память ограничена. → задача **Л5**.

Это тот же приём, что `CallerRunsPolicy` в теме 3, и то, что делает `Channel(capacity)` в корутинах
с `BufferOverflow.SUSPEND`. Цена — продюсер ждёт (растёт латентность на его стороне).

### Fan-in / fan-out
- **Fan-in**: несколько продюсеров пишут в одну очередь (она потокобезопасна). → задача **Л8**.
- **Fan-out**: несколько потребителей читают из одной очереди — параллельная обработка; каждый
  элемент достаётся ровно одному (ни потерь, ни дублей). → задача **С9**.

## 4. Стратегии с потерями: throttle, debounce, sample

Когда терять допустимо (UI-обновления, поиск, координаты пальца), выбирают, ЧТО именно оставить:

- **throttleFirst (leading)** — пропустить событие, только если с последнего эмита прошло ≥ интервала.
  «Реагируй сразу, но не чаще раза в N мс» (антидребезг кнопки). → задача **С11**.
- **debounce (trailing)** — эмитить значение, только когда после него `quiet` мс **не было** новых.
  Всплеск схлопывается в последнее значение. «Поиск, когда пользователь замолчал». → задача **С12**.
- **sample / throttleLatest** — каждый тик периода отдавать **последнее** значение окна. «Обновляй UI
  раз в кадр, показывая самое свежее». → задача **С13**.

Разница тонкая, но важная: throttle реагирует на **первое** в окне, sample — на **последнее**,
debounce — на **последнее после паузы**. На собесе любят просить объяснить отличие.

## 5. Конфляция (latest-wins) и drop-политики

- **Конфляция** — держать только **самое свежее** непрочитанное значение; пока потребитель занят,
  новые перезаписывают одно и то же место. Промежуточные теряются, но потребитель никогда не
  отстаёт. Так работает **`StateFlow`** и `Channel(CONFLATED)` / `.conflate()`. → задачи **С10, СЛ20**.
- **DROP_OLDEST** — буфер ёмкости N; при переполнении выбрасываем самое старое (храним свежие N).
  → задача **С14**.
- **DROP_LATEST** — при переполнении выбрасываем новое (храним ранние N). → задача **С15**.

Выбор политики — про смысл данных: для «текущего состояния» (позиция, прогресс) нужен свежак
(конфляция/DROP_OLDEST); для «нельзя пропустить начало» — DROP_LATEST. Это ровно перечень
`BufferOverflow` у корутин: `SUSPEND` (§3), `DROP_OLDEST`, `DROP_LATEST`.

## 6. Батчинг: пропускная способность вместо задержки

Если каждая операция дорогая (запись в БД, сетевой вызов), **батчинг** амортизирует её: копим
элементы и обрабатываем пачкой.
- **по количеству** — группы по N (одна запись на N элементов). → задача **СЛ16**.
- **по времени** — окна фиксированной ширины (`buffer(timespan)`). → задача **СЛ17**.

Батчинг увеличивает задержку (ждём наполнения пачки), но резко поднимает throughput — классический
размен «латентность ↔ пропускная способность».

## 7. Credit-based backpressure (Reactive Streams / Flow)

Самый «правильный» backpressure — когда **потребитель сам просит** столько, сколько потянет:
`request(n)`. Продюсер не имеет права эмитить больше суммарно запрошенного. Никаких безграничных
очередей, никакой потери — спрос управляет предложением. Так устроены **Reactive Streams**
(`Subscription.request`), RxJava `Flowable`, и по духу — suspend-эмиссия в корутинном `Flow`
(медленный `collect` естественно тормозит `emit`). → задача **СЛ18**.

## 8. Операторы композируются

Реальные пайплайны — это цепочки операторов. Например: `throttleFirst` (ограничить частоту
UI-событий) → `batchByCount` (сгруппировать в одну запись). → задача **СЛ19**. Именно так выглядит
код на `Flow`/Rx: `flow.debounce(300).distinctUntilChanged().buffer(...)`. Понимая механику каждого
оператора, ты осознанно собираешь конвейер под требования (свежесть? полнота? латентность? память?).

## 9. Где это в Android

- **`Flow`/`Channel`** — `buffer(capacity, onBufferOverflow)`, `conflate()`, `debounce()`, `sample()`,
  suspend-backpressure. Всё из этой темы — под капотом.
- **`StateFlow`** — конфляция + всегда есть текущее значение.
- **RxJava** — `Flowable` с `BackpressureStrategy` (BUFFER/DROP/LATEST/MISSING), операторы
  `throttleFirst`/`debounce`/`sample`/`buffer`.
- **`Handler`/`MessageQueue`** — безграничная очередь (тема 1): осторожно, backpressure нет.
- Сенсоры/локация, логгеры, аналитика, real-time сокеты — всё требует явной стратегии.
