# Тема 8. Фоновое выполнение и гарантии

> Современный Android жёстко экономит батарею и оперативку, поэтому «просто запустить фоновый поток»
> больше не работает: систему интересует, **переживёт ли работа смерть процесса и перезагрузку**, не
> разбудит ли она железо зря, и не крутится ли она, когда пользователь ушёл. Отсюда Doze, App Standby
> buckets, лимиты фоновых сервисов и целый планировщик (WorkManager/JobScheduler) с ограничениями,
> ретраями и цепочками. Для senior это обязательный минимум: чем гарантировать отложенную работу и
> почему `new Thread()` — не ответ.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt), прогоняя тесты:
> `./gradlew test --tests "handbook.android.background.*"`. Застрял — [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Модель детерминирована ([`Model.kt`](Model.kt)): API запуска, App Standby корзины, constraints,
> backoff, состояния и результаты work-задач, политики уникальности. Реальные планировщики — в
> системе; законы (гарантии, ограничения, ретраи) те же.

## 1. Проблема: голый поток ничего не гарантирует

`new Thread { … }.start()` (или `Executor`) живёт ровно столько, сколько **процесс**. Система убивает
фоновые процессы под давлением памяти в любой момент — и работа обрывается **без рескедулинга**. Такой
поток не переживает выход из приложения, не говоря о перезагрузке; он игнорирует Doze/лимиты и легко
жрёт батарею. → задача **Л8**. Для «сделай и забудь прямо сейчас, недолго» — ок; для **гарантированной
отложенной** работы нужен планировщик. → задача **Л1**.

## 2. Doze и App Standby

Две системы экономии, введённые с Android 6+:

- **Doze** — когда устройство лежит без движения с выключенным экраном, система периодически впадает в
  глубокий сон, **откладывая** фоновую работу, сеть и алармы до редких **maintenance-окон**. Обычная
  отложенная работа ждёт; **foreground service** и (в пределах квоты) expedited-работа — нет. → задача **Л4**.
- **App Standby buckets** — система классифицирует приложение по частоте использования: `ACTIVE` →
  `WORKING_SET` → `FREQUENT` → `RARE` → `RESTRICTED`. Чем «холоднее» корзина, тем **сильнее
  откладывается** его фоновая работа (окно deferral растёт от 0 до ~суток). → задача **С10**. Отсюда:
  запрошенная задержка не может быть меньше окна корзины. Не мучайте пользователя фоном — иначе
  скатитесь в `RESTRICTED`.

## 3. WorkManager: гарантированная отложенная работа

WorkManager — рекомендованный API для **отложенной работы, которая должна выполниться**, даже если
приложение закрыли или устройство перезагрузили. Он персистит задачи (в БД), поверх выбирает движок
(JobScheduler и т.п.), уважает Doze/Standby, умеет constraints/ретраи/цепочки/уникальность.

- `Worker.doWork()` исполняется на **фоновом потоке** — блокирующий код внутри допустим, главный поток
  не трогается. → задача **Л2**.
- Работа переживает reboot (как и JobScheduler). → задача **Л1**. Но WorkManager даёт **гарантию
  выполнения, а не немедленности**: он может отложить запуск.

## 4. Constraints — запускать только когда можно

Work-задаче задают **ограничения**: нужна сеть / безлимитная сеть / зарядка / не низкий заряд / idle /
не мало места. Задача стартует, только когда **все** ограничения выполнены. → задача **Л5**. Пока
условия не сошлись — она ждёт в очереди; полезно уметь показать, **какие именно** ограничения не
выполнены (диагностика). → задача **С11**. А по ленте меняющихся состояний устройства — определить,
**когда** условия сойдутся впервые. → задача **СЛ17**.

## 5. Результат работы и ретраи с backoff

`doWork()` возвращает один из трёх результатов:
- `Result.success()` / `Result.failure()` — **терминальны**;
- `Result.retry()` — задачу **ставят обратно** в очередь и перезапускают позже. → задача **Л6**.

Задержка перед повтором растёт по **backoff-политике**: `LINEAR` (initial × n) или `EXPONENTIAL`
(initial × 2ⁿ⁻¹), зажатая в границы `[10 c … 5 ч]`. → задачи **С9, СЛ16**. Экспонента быстро упирается
в потолок — суммарное ожидание раздувается. По ленте результатов повторов можно посчитать, за сколько
запусков дошли до успеха (или сдались на `failure`). → задача **СЛ18**.

## 6. Уникальная работа и политики

Часто нужно, чтобы работа с данным именем существовала **в одном экземпляре** (синхронизация, аплоуд).
`enqueueUniqueWork(name, policy, …)` при наличии существующей применяет [ExistingWorkPolicy]:
- `REPLACE` — отменить старую, поставить новую;
- `KEEP` — оставить старую, новую **проигнорировать**; → задача **Л7**
- `APPEND` — выполнить новую **после** старой (в цепочку).

Поставится ли новая работа — зависит от политики и наличия существующей. → задача **С13**.

## 7. Цепочки работ и каскадная отмена

`beginWith(a).then(b).then(c)` строит граф зависимостей. Пока родитель не завершён, потомок в состоянии
**BLOCKED**; после `SUCCEEDED` — становится `ENQUEUED`; если родитель `FAILED`/`CANCELLED` — потомок
**CANCELLED**. → задача **С12**. Провал одного звена **каскадно отменяет всех потомков** — по финальным
результатам узлов можно посчитать, сколько будет отменено. → задача **СЛ20**.

## 8. Foreground service — работа «прямо сейчас, видимо пользователю»

Если работа важна и должна идти **немедленно и непрерывно** (навигация, музыка, запись, аплоад по
кнопке) — это **foreground service**: он обходит фоновые лимиты и Doze, но обязан показать постоянную
**нотификацию** (пользователь видит, что приложение работает). → задача **Л3**. Начиная с Android 8,
запускать **обычные** фоновые сервисы из фона запрещено — используйте FGS или WorkManager.

## 9. Expedited-работа и квоты

WorkManager умеет **expedited** (срочную) работу — запускается почти сразу, даже в Doze, но в пределах
**квоты** времени на переднем плане, зависящей от App Standby корзины. Исчерпал квоту → задача
**деградирует** до обычной отложенной. → задача **С14**.

## 10. JobScheduler под капотом и его лимиты

WorkManager на многих версиях использует **JobScheduler**. У него есть системные лимиты, в т.ч. **число
запланированных задач на приложение** (~100) — перебор бросает исключение. → задача **С15**. Одна из
причин предпочитать WorkManager: он абстрагирует такие детали и батчит работу.

## 11. Коалесинг будильников (AlarmManager + Doze)

Точные будильники — через `AlarmManager`, но система **коалесирует** (батчит) неточные алармы: несколько
срабатываний в одном временно́м окне будят железо **один раз**. → задача **СЛ19**. Мораль: не просите
точное время без нужды (`setExact`/`setExactAndAllowWhileIdle` требуют разрешений и бьют по батарее) —
неточные алармы дешевле, потому что группируются.

## 12. Практические выводы

- Гарантированная отложенная работа → **WorkManager** (переживает reboot, уважает Doze/Standby, ретраит).
- «Прямо сейчас, видимо пользователю» → **foreground service** (+ нотификация).
- Не запускай фоновые сервисы из фона; голый `Thread` — только для короткой неважной работы.
- Вешай **constraints** (сеть/зарядка), не поллингуй — жди условий.
- Ретраи — через `Result.retry()` + backoff; не крути ретраи вручную в цикле.
- Уникальную работу ставь через `enqueueUniqueWork` с осознанной политикой.
- Меньше будишь железо (батчинг алармов, неточное время) — меньше жрёшь батарею и не падаешь в `RESTRICTED`.
