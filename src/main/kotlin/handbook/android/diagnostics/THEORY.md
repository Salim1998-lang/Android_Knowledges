# Тема 10. Диагностика многопоточности

> Писать многопоточный код — половина дела; senior должен уметь **разобрать инцидент**: почему на
> проде ANR, откуда jank, кто держит лок, есть ли дедлок. Инструменты для этого: `StrictMode` (ловит
> запрещённое на главном потоке), **thread dump / ANR-трейс** (кто в каком состоянии, кто держит и кто
> ждёт лок), **Perfetto/systrace** (где горит время кадра). Ключевой навык — читать эти артефакты как
> граф «кто кого ждёт» и находить в нём цикл (дедлок) или корень (виновник ANR).
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt), прогоняя тесты:
> `./gradlew test --tests "handbook.android.diagnostics.*"`. Застрял — [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Модель детерминирована ([`Model.kt`](Model.kt)): состояния потоков, операции на главном, penalty
> StrictMode, события трассировки, строки thread dump. Реальные дампы/трейсы — из рантайма; логика
> анализа (цикл, цепочка, self-time) — та же.

## 1. StrictMode: ловим запрещённое на главном потоке

`StrictMode` — детектор «плохих» вещей в debug-сборке:
- **`ThreadPolicy`** ловит на **главном** потоке медленные операции — **дисковый ввод-вывод и сеть**
  (но не обычный CPU-код). → задачи **Л1, С15**.
- **`VmPolicy`** ловит утечки процесса: незакрытые `Closeable`/курсоры, утёкшие Activity/SQLite-объекты.
  → задача **Л6**.

Реакция — **penalty**, и их можно комбинировать: `penaltyLog`, `penaltyDialog`, `penaltyDropBox`,
`penaltyDeath`. `penaltyDeath` **роняет** приложение — удобно в отладке, чтобы не пропустить нарушение;
в релизе так пользователей не убивают. → задача **Л2**. Из набора penalty «срабатывает» эффект по самой
строгой (`LOG < DIALOG < DROPBOX < DEATH`). → задача **С14**.

## 2. Состояния потоков в дампе

`Thread.State` в дампе говорит, чем занят поток:
- **RUNNABLE** — реально исполняется (или готов). → задача **Л5**.
- **BLOCKED** — ждёт захвата монитора (`synchronized`), который держит кто-то другой. → задача **Л3**.
- **WAITING / TIMED_WAITING** — ждёт условие/`wait`/`park`/таймаут.
- **TERMINATED / NEW** — завершён / ещё не стартовал.

Куча потоков в **BLOCKED** на одном локе — сигнал contention или дедлока. → задача **С11**. Ключевые
поля строки дампа: какие локи поток **держит** и какой лок **ждёт** — из них строится граф ожиданий.

## 3. Perfetto / systrace: где горит время

`Trace.beginSection("name")` / `Trace.endSection()` расставляют **вложенные** секции, видимые в Perfetto
и systrace. Правила чтения:
- секции — как скобки: каждый `begin` закрывается парным `end` (LIFO); незакрытая секция ломает трассу.
  → задача **С9**.
- глубина вложенности = длина синхронного стека работы; глубокий стек на главном потоке за кадр —
  подозрительно. → задача **С12**.
- главное для оптимизации — **собственное (self / exclusive) время** секции: сколько времени провела
  именно она, **без** вложенных подсекций. Это показывает, где реально «горит» кадр, а не в подвызовах.
  → задача **СЛ18**.

## 4. ANR-трейс: с чего начинать

При ANR система пишет трейс всех потоков; читать начинают с **главного** потока (`"main"`) — именно его
затык дольше порога (ввод ~5 с) и вызывает ANR. → задачи **Л4, Л8**. Смотрим стек main:
- если он в **RUNNABLE** и крутит тяжёлый метод — тяжёлая работа на UI-потоке;
- если он **BLOCKED/WAITING** на локе — надо найти, **кто держит** этот лок. → задача **С13** (виновник
  на один шаг).

## 5. Раскрутка корня ANR по цепочке

Часто виновник не на расстоянии одного шага: main ждёт лок у потока T1, а T1 сам ждёт лок у T2… Идём по
цепочке «ждёт лок → его держатель», пока не упрёмся в поток, который **сам ничего не ждёт** (RUNNABLE и
`waitsForLock == null`) — это **конечный виновник** (например, застрявший на сети IO-поток, из-за
которого стоит вся цепочка). → задача **СЛ19**. Если цепочка **замкнулась** в цикл — это уже дедлок
(см. §6), и «корня» нет.

Длина такой цепочки = глубина каскада блокировки: сколько потоков стоят паровозиком друг за другом.
→ задача **СЛ20**.

## 6. Детект дедлока = цикл в графе «кто кого ждёт»

Построй ориентированный граф: ребро **поток → держатель** лока, которого поток ждёт. **Дедлок** ⇔ в
графе есть **цикл** (A ждёт лок у B, B ждёт лок у A; или длиннее). → задачи **Л7, СЛ16**. Поиск — обход
в глубину с множеством вершин «в текущем стеке» (ребро назад в стек = цикл). Полезно уметь назвать
**конкретные** потоки, попавшие в дедлок (те, из которых по рёбрам можно вернуться в самих себя) — их и
показывают в отчёте. → задача **СЛ17**.

Профилактика (из темы `java.concurrency`): **глобальный порядок захвата локов**, `tryLock` с таймаутом,
меньше вложенных `synchronized`. Диагностика лишь подтверждает то, что предотвращается дисциплиной локов.

## 7. Практические выводы

- Включай **`StrictMode`** в debug (`penaltyDeath`) — лови диск/сеть на главном и утечки рано.
- Читая дамп: смотри **состояние** потока + что он **держит/ждёт**; куча BLOCKED = contention/дедлок.
- ANR: старт с **main**; если он на локе — иди по цепочке до **корня** (кто ни на кого не ждёт).
- **Дедлок = цикл** в графе ожиданий; предотвращай порядком локов, а не только лови постфактум.
- В Perfetto оптимизируй по **self-time** секций, а не по суммарному (оно включает подвызовы).
- Расставляй `Trace.beginSection`/`endSection` **парно** (лучше через `try/finally`), иначе трасса врёт.
