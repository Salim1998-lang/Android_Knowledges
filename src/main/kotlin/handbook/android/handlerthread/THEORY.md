# Тема 2. Фоновые Handler-потоки (`HandlerThread`)

> Тема 1 показала: у главного потока есть `Looper`/`MessageQueue`/`Handler`. Но `Looper` — не
> привилегия главного потока. `HandlerThread` — это **готовый рабочий поток со своим циклом
> событий**, куда можно слать `Runnable`/`Message`. Его берут ради трёх гарантий: **сериализации**,
> **thread confinement** и управляемого **жизненного цикла**.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.android.handlerthread.*"`. Застрял —
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Здесь мы работаем с НАСТОЯЩИМИ потоками через учебный [`LooperThread`](Model.kt) — минимальный
> аналог `HandlerThread` (реальный `Thread` + FIFO-цикл). Гарантии и API 1:1 с `android.os.HandlerThread`.

## 1. Что такое `HandlerThread` и зачем он

Обычный `Thread` выполняет один `run()` и умирает. Если нужно **много раз** подкидывать ему работу
(и чтобы она шла по порядку, на одном потоке), заводят поток с циклом событий:

```kotlin
val ht = HandlerThread("io").apply { start() }   // 1) поток стартует и внутри вызывает Looper.prepare()+loop()
val handler = Handler(ht.looper)                 // 2) getLooper() БЛОКИРУЕТ, пока Looper не готов
handler.post { /* работа на потоке "io" */ }     // 3) шлём задачи сколько угодно раз
// ...
ht.quitSafely()                                  // 4) завершаем, когда поток больше не нужен
```

Ключевой момент — шаг 2: `ht.looper` (`getLooper()`) **ждёт**, пока запущенный поток успеет создать
`Looper`. Поэтому `Handler(ht.looper)` до `start()` невозможен — `Looper`'а ещё нет. В нашей модели
это отражено так: `post` до `start()` возвращает `false`. → задача **Л4**.

Типичные потребители `HandlerThread` в Android: доступ к `Camera`/`Camera2` (коллбэки должны идти
на выделенный поток), работа с железом/сенсорами, последовательная запись в `SQLite`,
`IntentService` (внутри — `HandlerThread`).

## 2. Три гарантии, ради которых его берут

### 2.1. Сериализация (один поток — по одной задаче)
Все задачи одного `Looper`'а лежат в одной очереди и выполняются **строго по очереди**. Отправил
`a`, `b`, `c` — так они и выполнятся: `a`, потом `b`, потом `c`. → задачи **Л1, СЛ20**.

### 2.2. Thread confinement (замыкание на поток)
Все задачи выполняются на **одном и том же** потоке — потоке `Looper`'а, а НЕ на потоке того, кто
вызвал `post` (постить можно с любого потока — очередь потокобезопасна, → задача **С13**). Отсюда
мощное следствие: **состояние, к которому обращаются только из задач этого потока, не нуждается в
синхронизации**. Никаких `synchronized`/`volatile`/атомиков — потому что нет параллелизма: доступ
всегда с одного потока, по одной задаче. → задачи **Л2, Л6**.

```kotlin
// counter — обычный Int без volatile/локов. Гонки нет: все ++ идут с одного потока по очереди.
var counter = 0
repeat(1000) { handler.post { counter++ } }
```

Это альтернатива блокировкам из [`handbook.java.concurrency`](../../java/concurrency/THEORY.md): вместо
того чтобы защищать общее состояние `synchronized`, его **запирают на один поток** (single-thread
confinement) — и синхронизация становится не нужна. Тот же приём — под капотом `Dispatchers` у корутин.

### 2.3. Happens-before и `join()`
Между двумя последовательными задачами одного потока есть отношение **happens-before**: запись в
задаче N гарантированно видна задаче N+1. А `thread.join()` (или `quitSafely()` + `join()`) создаёт
happens-before между потоком и тем, кто дождался: после `join` вызывающий видит все записи задач.
Поэтому в задачах этой темы мы читаем результат **после** `join()` — без `volatile`. → задача **Л8**.

## 3. Жизненный цикл: `quit()` vs `quitSafely()`

`HandlerThread` живёт, пока крутится его `Looper`. Остановить — двумя способами:

| Метод | Что делает с очередью | Когда |
|-------|-----------------------|-------|
| `quit()` | **бросает** все ещё не обработанные сообщения, немедленно останавливает цикл | когда результат уже не нужен (экран закрыли) |
| `quitSafely()` | **дорабатывает** уже поставленные сообщения (готовые к исполнению), потом останавливает | когда важно не потерять поставленную работу |

После любого `quit*` `Handler` этого потока больше **не принимает** сообщения (`post` вернёт `false`).
→ задачи **Л5, С9, С10**.

Различие `quit`/`quitSafely` — любимый вопрос на собесе. В модели `LooperThread`:
- `quitSafely()` кладёт маркер в **хвост** очереди — всё, что стоит перед ним, отработает (FIFO);
- `quit()` **очищает** очередь и кладёт маркер выхода — ожидающее теряется.

> ⚠️ **Не забывай завершать `HandlerThread`.** Незавершённый поток живёт до конца процесса — это
> утечка потока (и удержание всего, на что ссылались его сообщения). Обычно `quitSafely()` в
> `onDestroy`/`onCleared`.

## 4. Обмен между потоками: round-trip на главный поток

Самый частый паттерн: посчитать тяжёлое на фоне и **вернуть результат на главный поток** (только там
можно трогать UI). Делается вложенным `post`:

```kotlin
val main = Handler(Looper.getMainLooper())
bgHandler.post {
    val result = heavyWork()          // на фоновом потоке
    main.post { view.render(result) } // назад на главный
}
```

Это и есть «ручной» механизм, который прячут за собой `runOnUiThread`, `LiveData.postValue`,
`Dispatchers.Main`. → задачи **С11, СЛ18** (запрос-ответ с корреляцией по id).

## 5. Много `Handler`'ов — один `Looper`

На один `Looper` можно повесить сколько угодно `Handler`'ов — очередь и поток у них **общие**.
Порядок выполнения — глобальный FIFO по времени постановки, независимо от того, какой `Handler`
положил сообщение. → задача **С12**. Разные `Handler`'ы удобны, чтобы:
- различать источники сообщений (`what`/токены — снимать пачками, см. тему 1);
- дать разным подсистемам свой «пульт» к одному рабочему потоку.

## 6. Backpressure: один потребитель — растущая очередь

`HandlerThread` — **один** потребитель. Если продюсер кладёт задачи быстрее, чем поток успевает их
обрабатывать, очередь растёт: задачи не теряются и порядок сохраняется, но **задержка** до их
выполнения увеличивается. → задача **С14**.

Опасность: очередь `MessageQueue` **неограниченная** — при устойчивом переполнении это рост памяти
и, в пределе, OOM. Настоящий backpressure (ограниченные очереди, conflation, отбрасывание) —
отдельная тема модуля (`handbook.android.queues`). Здесь важно понять сам факт: последовательный
потребитель превращает всплеск нагрузки в задержку.

## 7. Параллелизм через шардирование

Один `HandlerThread` не параллелит работу (он один). Чтобы получить параллелизм, но сохранить
confinement, работу **шардируют**: несколько `HandlerThread`, задачи раскидываются детерминированно
(по ключу/хэшу), и каждый поток владеет своим куском состояния без локов. → задача **С15**.

Это тот же принцип, что `newSingleThreadExecutor` на шард (например, «по пользователю» или «по
партиции»): параллелизм между шардами, сериализация внутри шарда. Когда нужен просто пул воркеров —
это `ExecutorService` (тема `handbook.android.pools` и [`handbook.java.concurrenthigh`](../../java/concurrenthigh/THEORY.md)).

## 8. Конвейеры и координация нескольких потоков

Несколько `HandlerThread` соединяют в **конвейер**: каждая стадия делает свою работу и `post`'ом
передаёт результат следующей. Классика — обработка кадра: `capture-thread` → `process-thread` →
`ui-thread`. Каждая стадия сериализована и замкнута на свой поток. → задача **СЛ16**.

Координацию между потоками строят на **сообщениях** (хендофф), а не на разделяемых локах: например,
пинг-понг двух потоков, перекидывающих токен, — задача **СЛ17**. Это дешевле и безопаснее блокировок.

## 9. Жизненный цикл и «работа, пережившая владельца»

Отложенная/фоновая задача может выполниться уже **после** того, как экран уничтожен. Если она
обратится к мёртвой `Activity`/`View` — краш или утечка. Два приёма:
- снимать задачи при уничтожении (`removeCallbacksAndMessages(null)` / `quitSafely()`), см. тему 1;
- либо проверять в начале задачи, «жив ли владелец» (флаг/`WeakReference`), и тихо выходить.
→ задача **СЛ19**. Подробнее про утечки — [`handbook.java.memory`](../../java/memory/THEORY.md) и
будущая тема `handbook.android.lifecycle`.

## 10. `HandlerThread` в 2020-е: где он и где корутины

`HandlerThread` — низкоуровневый, «честный» примитив. В современном коде его роль часто закрывают:
- **корутины** + `Dispatchers`/`newSingleThreadContext` — тот же confinement, но декларативно
  (модуль «Корутины»);
- `Executors.newSingleThreadExecutor()` — если не нужен именно `Looper`/`Handler`;
- `WorkManager` — для гарантированной фоновой работы (тема `handbook.android.background`).

Но понимать `HandlerThread` обязательно: на нём построены `Camera2`, многие системные API и, главное,
он делает наглядной идею **«сериализация + confinement вместо локов»**, которую корутины лишь прячут.
