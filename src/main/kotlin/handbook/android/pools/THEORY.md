# Тема 3. Пулы потоков в Android (`ThreadPoolExecutor`)

> Темы 1–2 дали один поток с циклом (`Looper`/`HandlerThread`). Но когда нужен **параллелизм** —
> считать на всех ядрах, тянуть десятки сетевых запросов — заводят **пул потоков**. Пул
> переиспользует потоки (создание потока дорого: ~1–2 МБ стека + системный вызов) и ограничивает их
> число. В Android один и тот же `ThreadPoolExecutor` крутится под капотом `AsyncTask`,
> `Dispatchers.IO`/`Default`, `WorkManager`, Retrofit/OkHttp.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt), прогоняя тесты:
> `./gradlew test --tests "handbook.android.pools.*"`. Застрял — [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Работаем с НАСТОЯЩИМ `java.util.concurrent`. Помощник [`Gate`](Model.kt) нужен только чтобы
> детерминированно «занять» потоки и посмотреть на состояние пула. Различие с
> [`handbook.java.concurrenthigh`](../../java/concurrenthigh/THEORY.md): там — API `ExecutorService`/
> `Future`/`CompletableFuture`, здесь — **как сконфигурировать пул и почему**.

## 1. Зачем пул, а не «поток на задачу»

Антипаттерн — `Thread { work() }.start()` на каждую задачу:
- дорого: создание/уничтожение потока + ~1 МБ стека каждый;
- неограниченно: всплеск нагрузки → тысячи потоков → OOM и деградация от переключений контекста;
- нет управления: не отменить, не измерить, не приоритизировать.

Пул решает всё это: держит **фиксированное** число переиспользуемых потоков и **очередь** задач.
→ задача **СЛ20** (пул = жёсткий потолок параллелизма), **Л6** (базовое использование).

## 2. Sizing: сколько потоков?

Зависит от типа работы:

- **CPU-bound** (счёт, парсинг, декодинг): потоков ≈ `число_ядер` (иногда `+1` на подстраховку от
  редких простоев на промахах кэша). Больше — только лишние переключения контекста. → задача **Л1**.
- **IO-bound** (сеть, диск, БД): потоки бóльшую часть времени **ждут**, не грузя CPU, поэтому их
  имеет смысл больше. Формула Брайана Гётца:

  ```
  N = N_ядер × U × (1 + W/C)
  ```
  где `U` — целевая загрузка CPU (0..1), `W` — время ожидания, `C` — время счёта. Для IO с `W ≫ C`
  число потоков кратно больше числа ядер. → задача **Л2**.

Именно поэтому у корутин **`Dispatchers.Default`** ≈ числу ядер (CPU-work), а **`Dispatchers.IO`** —
64+ потоков (IO-work). Это не магия, а те же две формулы.

## 3. `ThreadPoolExecutor`: семь параметров

`Executors.newFixedThreadPool`/`newCachedThreadPool` — это обёртки над `ThreadPoolExecutor`. Чтобы
понимать поведение (и не нарваться на подвох из §4), конфигурируй его явно:

```java
new ThreadPoolExecutor(
    corePoolSize,      // «постоянные» потоки
    maximumPoolSize,   // максимум потоков под пиком
    keepAliveTime, unit,   // сколько простаивать лишним (сверх core) потокам перед смертью
    workQueue,             // очередь задач (BlockingQueue)
    threadFactory,         // как создавать потоки (имя, приоритет, daemon)
    handler                // rejection-политика при переполнении
);
```

### `ThreadFactory` — имена, приоритет, daemon
Дефолтные потоки называются `pool-1-thread-3` — бесполезно в ANR-трейсе. Своя фабрика даёт:
- **осмысленное имя** (`"disk-io-1"`) → читаемые трейсы и профайлер; → задача **Л3**;
- **пониженный приоритет** для фона: `android.os.Process.setThreadPriority(THREAD_PRIORITY_BACKGROUND)`
  (на JVM аналог — `Thread.setPriority`), чтобы пул не отбирал CPU у UI-потока; → задача **Л4**;
- **daemon**-флаг, чтобы забытый пул не держал процесс. → задача **Л5**.

## 4. ⚠️ Главный подвох: как пул решает, куда деть задачу

Алгоритм `execute(task)` — источник самого частого недопонимания на собесе. По шагам:

```
1. потоков < corePoolSize?           → создать НОВЫЙ поток под эту задачу
2. иначе, очередь приняла задачу?     → задача ЖДЁТ в очереди
3. иначе, потоков < maximumPoolSize? → создать НОВЫЙ поток (сверх core)
4. иначе                              → ОТКАЗ (rejection handler)
```

Критическое следствие: **новые потоки сверх `core` поднимаются, только когда очередь ЗАПОЛНЕНА** (шаг 3
после шага 2). Отсюда подвох:

> Если очередь **безграничная** (`LinkedBlockingQueue` без ёмкости, как в `newFixedThreadPool`), шаг 2
> **всегда** успешен → шаг 3 недостижим → пул **никогда** не вырастет выше `corePoolSize`, а
> `maximumPoolSize` не имеет смысла. Задачи копятся в очереди без ограничения (риск OOM).

→ задачи **С9** (рост до core), **С10** (безграничная очередь ⇒ потолок = core, подвох),
**С11** (ограниченная очередь ⇒ рост до max).

Три «преднастроенных» пула через эту призму:
| `Executors.*` | core / max | очередь | смысл |
|---------------|-----------|---------|-------|
| `newFixedThreadPool(n)` | n / n | безграничная | ровно n потоков, очередь растёт (см. подвох) |
| `newCachedThreadPool()` | 0 / ∞ | `SynchronousQueue` (ёмкость 0) | шаг 2 всегда мимо → поток под каждую задачу; хорошо для коротких IO, опасно для всплесков |
| `newSingleThreadExecutor()` | 1 / 1 | безграничная | сериализация + порядок (как `HandlerThread`) → задача **СЛ17** |

## 5. Rejection-политики: что делать при переполнении

Когда заняты и все потоки (`max`), и очередь — срабатывает `RejectedExecutionHandler`:

| Политика | Поведение | Когда |
|----------|-----------|-------|
| `AbortPolicy` (по умолчанию) | бросает `RejectedExecutionException` | нужно узнать о перегрузке явно |
| `CallerRunsPolicy` | выполняет задачу на потоке ОТПРАВИТЕЛЯ | нужен backpressure без потерь |
| `DiscardPolicy` | молча выбрасывает новую задачу | потеря допустима (например, метрики) |
| `DiscardOldestPolicy` | выбрасывает самую старую из очереди, ставит новую | важнее свежие данные |

→ задачи **С12** (Abort), **С13/СЛ18** (CallerRuns), **С14** (Discard).

**`CallerRunsPolicy` — рецепт backpressure.** Ограниченная очередь + `CallerRunsPolicy`: при переливе
задача исполняется на потоке продюсера → продюсер **сам притормаживается** (не может слать быстрее, чем
пул успевает), ничего не теряется и не растёт очередь. Это дефолтный «безопасный» пул для конвейеров.
→ задача **СЛ18**.

## 6. Жизненный цикл пула: `shutdown` vs `shutdownNow`, прогрев

- `shutdown()` — «не принимать новые задачи, доработать уже принятые». `awaitTermination(t, unit)` —
  дождаться завершения. Всегда завершай пул, иначе его непотоки-daemon держат процесс.
- `shutdownNow()` — прервать выполняющиеся (`Thread.interrupt`) и **вернуть список незапущенных**
  задач (их можно перепланировать). → задача **С15**. (Важно: код в задачах должен реагировать на
  `interrupt`, иначе прервать не выйдет — см. кооперативную отмену в модуле «Корутины».)
- `prestartAllCoreThreads()` — «прогреть» пул заранее: создать core-потоки до первой задачи, убрав
  латентность холодного старта. → задача **СЛ16**.
- `allowCoreThreadTimeOut(true)` + `keepAliveTime` — разрешить core-потокам умирать при простое
  (пул сжимается до 0), экономя ресурсы у редко используемого пула.

## 7. Изоляция пулов (Android-важное)

Никогда не смешивай **блокирующий IO** и **CPU-счёт** в одном пуле: пачка зависших сетевых вызовов
займёт все потоки и **заморит голодом** CPU-работу (и наоборот). Держи **раздельные** пулы под разные
типы работы — тогда насыщение одного не влияет на другой. → задача **СЛ19**.

Это ровно причина, по которой у корутин `Dispatchers.IO` и `Dispatchers.Default` — **разные**
пулы (хоть и делят потоки через `limitedParallelism`). Тот же принцип: не блокируй CPU-диспетчер IO-операциями.

## 8. Пулы в экосистеме Android

- **`AsyncTask`** (устарел): `SERIAL_EXECUTOR` (по одной задаче) по умолчанию и общий
  `THREAD_POOL_EXECUTOR` — исторический источник багов «почему мои AsyncTask'и идут по очереди».
- **`Dispatchers.IO`/`Default`** — те же `ThreadPoolExecutor` с sizing из §2.
- **OkHttp `Dispatcher`** — свой пул + лимиты на число одновременных запросов (`maxRequests`).
- **`WorkManager`** — пул под фоновую работу (`Configuration.taskExecutor`).

Понимая `ThreadPoolExecutor`, ты понимаешь их все — это один и тот же механизм с разными настройками.
