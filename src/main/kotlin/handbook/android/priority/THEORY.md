# Тема 4. Приоритеты и планирование потоков

> Пул (тема 3) даёт потоки, но **кому из готовых потоков дать процессор прямо сейчас** — решает
> планировщик ОС. На Android это планировщик Linux (**CFS** + классы реального времени), а «ручка»
> управления — **nice**-приоритет через `android.os.Process.setThreadPriority(...)`. Понимать это
> обязательно на сеньоре: отсюда и джанк («фон отъел CPU у UI»), и зависания (инверсия приоритетов),
> и голодание фоновых задач.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt), прогоняя тесты:
> `./gradlew test --tests "handbook.android.priority.*"`. Застрял — [`solutions/Solutions.kt`](solutions/Solutions.kt).

> ⚠️ Реальный OS-планировщик недетерминирован, а `java.lang.Thread.setPriority` на JVM — лишь
> **подсказка**, которую планировщик обычно игнорирует. Поэтому здесь мы работаем с
> **детерминированной моделью** планировщика ([`Model.kt`](Model.kt)): те же законы (nice→вес→доля
> CPU, CFS-vruntime, cgroup, RT-классы), но без флака.

## 1. Два разных «приоритета» — не перепутай

| | `java.lang.Thread` priority | Android / Linux nice |
|---|---|---|
| Диапазон | 1..10 (`MIN`/`NORM`/`MAX`) | −20..19 |
| Кто выше | больше = выше | **меньше = выше** (контринтуитивно!) |
| Как задать | `thread.priority = ...` | `Process.setThreadPriority(TID, nice)` |
| Влияние на Android | почти нулевое (подсказка) | **реальное** (через ядро) |

Главная ловушка новичка: `thread.setPriority(Thread.MAX_PRIORITY)` на Android **почти ничего не
делает**. Настоящий рычаг — `Process.setThreadPriority`, оперирующий **nice**. И правило nice
обратное: **чем меньше число, тем важнее поток**. → задачи **Л1, Л2**.

Константы `android.os.Process.THREAD_PRIORITY_*` (это nice-значения):

| Константа | nice | для чего |
|-----------|-----:|----------|
| `URGENT_AUDIO` | −19 | low-latency аудио (почти RT) |
| `AUDIO` | −16 | аудио |
| `URGENT_DISPLAY` | −8 | ввод + анимация текущего кадра |
| `DISPLAY` | −4 | UI/отрисовка |
| `FOREGROUND` | −2 | поток переднего плана |
| `DEFAULT` | 0 | обычный |
| `BACKGROUND` | 10 | **фоновая работа** |
| `LOWEST` | 19 | максимально уступчивый |

→ задачи **Л3, Л4**.

## 2. nice → вес → доля CPU (модель CFS)

Планировщик Linux — **CFS (Completely Fair Scheduler)**. Каждому nice сопоставлен **вес**; CPU
делится **пропорционально весам**. В модели:

```
weight(nice) = 1024 * 1.25^(-nice)      // 1024 = вес при nice 0 (NICE_0_LOAD)
доля потока  = weight / Σ weight(всех готовых потоков)
```

Каждый шаг nice меняет вес в ~1.25 раза (**≈ ±20% CPU за шаг**). Пример: два потока nice 0 и nice 0
делят CPU 50/50; nice −2 против nice 0 — уже ~61/39. → задачи **Л5, Л6, Л7**.

> Реальное ядро использует табличку `sched_prio_to_weight` (очень близкую к геометрии 1.25) — детали
> не важны, важен закон: **вес геометрически растёт при понижении nice**.

## 3. CFS изнутри: vruntime

Как CFS решает, кого запустить? У каждого потока есть **виртуальное время выполнения (vruntime)**.
Правило: **бежит поток с наименьшим vruntime** («наименее обслуженный — первым»). Отработав квант,
поток увеличивает свой vruntime на величину, **обратно пропорциональную весу**:

```
Δvruntime = NICE_0_LOAD / weight(nice) = 1.25^(nice)
```

Высокий nice (маленький вес) → vruntime растёт быстро → поток «убегает вперёд» и его выбирают реже.
Низкий nice → vruntime растёт медленно → выбирают чаще. → задачи **С9, С10**.

Два одинаковых потока при этом строго **чередуются** (A, B, A, B…) — это и есть «справедливость».
CFS **не морит голодом**: даже низкоприоритетный поток рано или поздно станет «наименее обслуженным»
и получит квант. Пропорции квантов сходятся к пропорциям весов. → задача **СЛ18**.

## 4. cgroups: второй уровень троттлинга фона

nice раздаёт CPU **внутри** группы. Но Android ещё кладёт фоновые приложения/потоки в отдельную
**cgroup**, которой суммарно выделена лишь малая доля CPU (в модели — множитель `0.05`). Поэтому
фоновый поток троттлится **дважды**: высоким nice **и** принадлежностью к background-cgroup. Даже при
одинаковом nice поток в foreground-cgroup получит кратно больше CPU, чем в background. → задачи
**Л8, С11, СЛ17**.

Практика: когда приложение уходит в фон, система перемещает его в background-cgroup — фоновые потоки
резко замедляются. Это одна из причин, почему «долгая работа в фоне» ненадёжна (см. тему
`handbook.android.background`).

## 5. Строгий приоритет и starvation

Противоположность CFS — **строгий приоритетный** планировщик: всегда бежит самый приоритетный
готовый поток и не уступает, пока не заблокируется. Плюс — предсказуемость для критичных задач;
минус — **голодание (starvation)**: низкоприоритетные потоки могут не получить CPU **никогда**, пока
высокоприоритетный занят. → задачи **С12, С13**.

CFS выбирает компромисс: приоритет влияет на **долю**, но не отменяет поток полностью. Строгий
приоритет живёт в **классах реального времени** (см. §7).

## 6. Инверсия приоритетов и наследование

Классическая ловушка многопоточности (её обсуждают на любом senior-собесе):

```
H (high) хочет лок L, который держит поток Low.
Появляется независимый M (mid), приоритетнее Low.
Планировщик вытесняет Low ради M → Low НЕ МОЖЕТ отпустить лок →
H, хоть и самый приоритетный, ждёт... фактически из-за M. Это ИНВЕРСИЯ приоритетов.
```

Инверсия возможна, когда есть mid, приоритетнее держателя лока. → задача **С14**.

**Лечение — priority inheritance (наследование приоритета):** пока Low держит лок, нужный H, он
**временно получает приоритет H** (эффективный nice = `min(nice_Low, nice_H)`). Теперь Low
приоритетнее M, быстро доделывает, отпускает лок — H продолжает. → задача **С15**. Наследование
**транзитивно** по цепочке удержаний (L→M→H): приоритет самого важного ждущего протягивается через
всю цепочку. → задача **СЛ19**. На Linux это делают futex'ы с PI; знаменитый баг Mars Pathfinder —
как раз непочиненная инверсия приоритетов.

## 7. Классы планирования: RT вытесняет обычные

У Linux есть **классы**: обычные потоки (`SCHED_OTHER`/CFS) и **реального времени**
(`SCHED_FIFO`/`SCHED_RR`). Любой готовый RT-поток **вытесняет все обычные целиком**, независимо от их
nice: пока есть runnable RT — бежит он. → задача **СЛ20**.

RT используют для аудио/сенсоров с жёсткими дедлайнами (`URGENT_AUDIO` близок к этому). Но это
опасный инструмент: RT-поток в busy-loop способен **заморозить систему** (он не уступит обычным
никогда). Поэтому RT-приоритеты выдаются скупо и только коротким, гарантированно уступающим задачам.

## 8. Практические выводы для Android

- **Всегда понижай приоритет фоновых потоков** до `THREAD_PRIORITY_BACKGROUND` (nice 10). Иначе фон
  идёт наравне с UI (nice `DISPLAY` −4) и **отъедает у него CPU → джанк**. Разница драматична: в
  модели UI получает ~71% против «незаниженного» фона и ~96% против правильно заниженного. → задача **СЛ16**.
- `Process.setThreadPriority()` действует на **вызывающий** поток (или на поток по TID) — вызывай его
  **внутри** фонового потока/задачи, а не снаружи.
- Пулы (тема 3) задавай через `ThreadFactory`, понижающую nice, — тогда весь фоновый пул уступает UI.
- Не полагайся на `java.lang.Thread.setPriority` для управления на Android — это подсказка, не рычаг.
- Корутинные `Dispatchers` не управляют nice напрямую — при необходимости понижай приоритет в
  `ThreadFactory` кастомного диспетчера.
