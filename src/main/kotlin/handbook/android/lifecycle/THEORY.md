# Тема 9. Потоки и жизненный цикл

> Фоновый поток не знает и не хочет знать про твой экран. А экран (Activity/Fragment/View) живёт по
> своим правилам: его создают, останавливают, **пересоздают при повороте** и уничтожают. Столкновение
> этих двух миров рождает самые частые баги Android-многопоточности: результат прилетает на **уже
> мёртвый** экран (крах/утечка), поворот **теряет** незавершённую работу, `Handler` с отложенным
> сообщением **держит Activity** в памяти. Управление этим стыком — то, что отличает senior.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt), прогоняя тесты:
> `./gradlew test --tests "handbook.android.lifecycle.*"`. Застрял — [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Модель детерминирована ([`Model.kt`](Model.kt)): состояния жизненного цикла ([LifecycleState] +
> [isAtLeast]), скоупы ([ScopeKind]), действие с результатом ([DeliverAction]), события LiveData
> ([LiveEvent]). Реальные Activity/ViewModel/LiveData — во фреймворке; правила те же.

## 1. Состояния жизненного цикла и «активность»

androidx `Lifecycle.State` упорядочен от «мертво» к «активно»:
`DESTROYED < INITIALIZED < CREATED < STARTED < RESUMED`. Сравнение — через `isAtLeast(...)`.
**Активным** (видим пользователю, можно трогать UI и доставлять обновления наблюдателям) считается
состояние **≥ STARTED**. → задача **Л1**. В `DESTROYED` доставлять результат некуда. → задача **Л3**.

## 2. Публикация результата на главный поток

UI можно трогать только с главного потока. Значит результат фоновой работы надо **перекинуть**
(`Handler(mainLooper).post`, `runOnUiThread`, `withContext(Main)`, `postValue`). → задача **Л2**. Но
одного «перекинуть на главный» мало: пока задача считала, экран мог **уничтожиться**. Поэтому решение
принимается по двум осям сразу — жив ли компонент и на каком мы потоке:

- `DESTROYED` → **DROP** (не доставляем, иначе крах/утечка);
- не главный поток → **POST_TO_MAIN**;
- иначе → **DELIVER**. → задача **С9**.

Порядок важен: **сперва проверь, жив ли компонент**, потом маршалируй.

## 3. Config change: Activity умирает, ViewModel живёт

При смене конфигурации (поворот, смена языка/темы) система по умолчанию **уничтожает и пересоздаёт**
Activity/Fragment. → задача **Л6**. Всё, что держало ссылку на *старый* экземпляр (фоновый колбэк,
`Handler`), теперь указывает на **стейл** — мёртвый объект. Незавершённая работа, запущенная в самой
Activity, **теряется/утекает**. → задача **С11**.

Лекарство — **`ViewModel`**: он **переживает** config change (система хранит его между пересозданиями и
очищает в `onCleared()`, когда экран уходит окончательно). → задача **Л5**. Поэтому долгую работу и
состояние держат в `ViewModel`, а не в Activity.

## 4. Скоупы корутин и их привязка

- **`lifecycleScope` / `viewLifecycleScope`** (`ScopeKind.LIFECYCLE`) отменяются при **DESTROY**
  компонента — а значит и при config change (Activity пересоздаётся). → задача **С13**. Работа,
  не завершённая к `onDestroy`, отменяется, результат не доставляется — обычно это ровно то, что нужно.
  → задача **СЛ19**.
- **`viewModelScope`** (`ScopeKind.VIEW_MODEL`) **переживает** config change и отменяется только в
  `onCleared()`. → сюда поднимают работу, которая должна пережить поворот.

## 5. Утечки `Handler`

Нестатический (внутренний/анонимный) `Handler` держит **неявную ссылку** на внешний класс — Activity.
Пока в очереди висит **отложенное** сообщение (`postDelayed`), сообщение → Handler → Activity удерживают
друг друга, и GC не может собрать экран. → задача **Л7**. Даже после `onDestroy` утечка длится, **пока
сообщение не сработает** — окно утечки = сколько сообщению ещё «висеть». → задача **СЛ17**.

Лечение: делай `Handler` **статическим** с `WeakReference` на Activity, и обязательно
`removeCallbacksAndMessages(null)` в `onDestroy`. → задача **С10**. WeakReference разрывает удержание,
но тогда колбэк на уже собранный компонент просто **не приходит** — это и есть желаемое поведение.
→ задача **С15**.

## 6. Стейл-колбэки после уничтожения

Любой зарегистрированный слушатель/колбэк (сенсоры, `BroadcastReceiver`, сетевые коллбэки, listeners),
не снятый в `onDestroy`, продолжит **прилетать на мёртвый экран** — крах или удержание в памяти. Сколько
таких стейл-срабатываний случится, зависит от того, **отписались ли** при уничтожении. → задача **СЛ20**.
Правило: **что подписал/запустил — отпиши/отмени** в парном методе жизненного цикла.

## 7. LiveData: только активным наблюдателям + sticky

`LiveData` — lifecycle-aware:
- обновления доставляются **только активным** наблюдателям (владелец ≥ STARTED); неактивный ничего не
  получает;
- когда наблюдатель **становится активным**, ему доставляется **последнее** значение (sticky-реплей);
- пока наблюдатель неактивен, несколько `setValue` **коалесируются** — хранится только последнее.
  → симуляция в задаче **СЛ16**.

Потоки: `setValue` — **только главный поток**; с фонового — `postValue`. → задачи **Л4, С12**. `postValue`
при пачке вызовов до диспатча оставляет **последнее** значение (коалесинг). → задача **Л8**. Поэтому
серия `postValue` может «проглотить» промежуточные значения — не рассчитывай, что увидишь каждое.

## 8. `repeatOnLifecycle` — сбор Flow по состоянию

`Flow` не lifecycle-aware сам по себе. Наивный `lifecycleScope.launch { flow.collect { … } }` продолжает
собирать **и в фоне** (экран невидим) — трата ресурсов и риск обновить невидимый UI. Правильно —
`repeatOnLifecycle(STARTED) { flow.collect { … } }`: сбор **активен только при ≥ STARTED** → задача
**С14**, и **перезапускается заново** при каждом возврате на экран (STARTED из неактивного). Сколько раз
сбор стартует за ленту переходов — считаемо. → задача **СЛ18**. `flowWithLifecycle` — обёртка того же.

## 9. Практические выводы

- Перед касанием UI из фона: **жив ли компонент** (≥ STARTED / не DESTROYED) → потом на главный поток.
- Долгую работу и состояние держи в **`ViewModel`** (переживает поворот), а не в Activity.
- `lifecycleScope` для работы, привязанной к экрану; `viewModelScope` — для переживающей config change.
- `Handler`: статический + `WeakReference`, `removeCallbacksAndMessages(null)` в `onDestroy`.
- Что подписал/запустил — **отпиши/отмени** в парном lifecycle-методе (иначе стейл-колбэки).
- `LiveData`: `setValue` на главном, `postValue` с фона (помни про коалесинг); доставка только активным.
- Собирай `Flow` через **`repeatOnLifecycle(STARTED)`**, а не голым `launch { collect }`.
