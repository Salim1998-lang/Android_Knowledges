# Тема 1. Главный поток и цикл событий (`Looper` / `Handler` / `MessageQueue`)

> Это фундамент всей многопоточности в Android: **любой** UI-код, `View`, коллбэки жизненного
> цикла, `postValue`, отрисовка кадра, доставка ввода — крутятся на **одном** потоке через **один**
> цикл сообщений. Пока не понимаешь его — не понимаешь ни jank, ни ANR, ни почему `Handler` течёт.
>
> Прочитай теорию, затем реши 20 задач в [`Tasks.kt`](Tasks.kt) (тела `TODO()`), прогоняя тесты:
> `./gradlew test --tests "handbook.android.looper.*"`. Застрял — сверься с
> [`solutions/Solutions.kt`](solutions/Solutions.kt).

> Мы моделируем механику `MessageQueue` детерминированно на JVM (тип [`Scheduled`](Model.kt)) —
> без Android SDK и эмулятора. Идеи 1:1 переносятся на настоящий `android.os.*`.

## 1. Зачем вообще цикл событий

У главного (UI) потока нет «тела функции», которое можно было бы выполнить и завершить. Приложение
должно **жить** и реагировать на события: касания, отрисовку, таймеры, результаты из фоновых
потоков. Классическое решение — **event loop**: бесконечный цикл, который достаёт события из
очереди и обрабатывает по одному.

Упрощённо весь Android-поток с UI — это:

```java
Looper.prepare();      // создать Looper + MessageQueue и привязать к текущему потоку
// ... создать Handler'ы ...
Looper.loop();         // бесконечно: взять сообщение → выполнить → повторить
```

`ActivityThread.main()` (точка входа процесса приложения) делает ровно это для главного потока.
`Looper.loop()` не возвращается никогда (до `quit()`) — поэтому «главный поток завис» = «цикл застрял
на одном сообщении».

## 2. Три кита

| Компонент | Роль | Сколько на поток |
|-----------|------|------------------|
| **`Looper`** | владеет циклом и `MessageQueue`; привязан к ОДНОМУ потоку через `ThreadLocal` | 0 или 1 |
| **`MessageQueue`** | упорядоченная по времени очередь `Message` (односвязный список по полю `when`) | 1 (внутри `Looper`) |
| **`Handler`** | «пульт»: кладёт сообщения в очередь своего `Looper` и обрабатывает их (`handleMessage`/`Runnable`) | много |

Ключевые связи:
- `Looper` **привязан к потоку** (`ThreadLocal<Looper>`). Один поток — максимум один `Looper`.
  Повторный `prepare()` → `RuntimeException("Only one Looper may be created per thread")`.
- `Handler` при создании захватывает `Looper` (по умолчанию — текущего потока, поэтому `new Handler()`
  на потоке без `Looper` падает; сейчас конструктор без `Looper` вообще deprecated — передавай
  `Handler(Looper.getMainLooper())` явно).
- **На каком потоке крутится `Looper` — на том и выполняется коллбэк**, независимо от того, с какого
  потока вызвали `handler.post(...)`. Это и есть способ «перепрыгнуть» на нужный поток.

```kotlin
// с любого фонового потока безопасно закинуть работу на главный:
val main = Handler(Looper.getMainLooper())
main.post { textView.text = "готово" }   // выполнится на UI-потоке
```

## 3. `MessageQueue` упорядочена по времени, а не по порядку `post`

Каждый `Message` несёт поле `when` — **абсолютный** момент срабатывания в миллисекундах
`SystemClock.uptimeMillis()`. `postDelayed(r, delay)` — это просто `when = uptimeMillis() + delay`,
а `post(r)` — это `postDelayed(r, 0)` → `when = uptimeMillis()`.

Очередь — односвязный список, отсортированный по `when` (при равенстве — FIFO по порядку вставки).
`Looper.loop()` всегда берёт **голову** списка:

```
post A (delay 100)   ─┐
post B (delay 0)      ├─►  очередь:  B(when=0) → C(when=50) → A(when=100)
post C (delay 50)    ─┘        порядок ВЫПОЛНЕНИЯ: B, C, A   (НЕ A, B, C!)
```

Отсюда важные следствия для собеса:
- Порядок `post` **не** равен порядку выполнения — решает `when`. → задачи **Л1, С9**.
- `postAtFrontOfQueue` ставит `when = 0` → лезет в начало, обгоняя всё. Мощно и опасно: в цикле
  такими можно «заморить голодом» остальную очередь. → задача **Л8**.
- Почему `uptimeMillis`, а не `currentTimeMillis`: uptime **монотонен** и не прыгает при смене
  системного времени/часовых поясов; но **замирает в deep sleep** — поэтому `postDelayed` НЕ годится
  для точных «разбуди через час», для этого есть `AlarmManager`/`WorkManager`.

## 4. Как крутится цикл: `next()` и блокирующий сон

Сердце — `MessageQueue.next()`. Псевдокод:

```
loop:
  now = uptimeMillis()
  msg = голова очереди
  if (msg != null && msg.when <= now) return msg          // готово — отдать на выполнение
  timeout = if (msg == null) -1 else (msg.when - now)      // сколько спать
  nativePollOnce(timeout)   // засыпаем на epoll; -1 = «спать, пока не разбудят enqueue/ввод»
  goto loop
```

- Если голова **готова** (`when <= now`) — вернуть немедленно (спать не нужно). → задача **Л5**.
- Если голова в будущем — спать ровно до её `when` (эффективно, без busy-wait). → задача **Л5**.
- Если очередь пуста — спать «бесконечно» (`timeout = -1`), пока новый `enqueueMessage` или событие
  ввода не сделает `nativeWake()`. Поток при этом **не жжёт CPU** — он реально спит в ядре (epoll).

Именно поэтому «idle»-приложение не греет батарею: цикл спит в `nativePollOnce`, а не крутится.

## 5. Отправка работы: перегрузки `Handler`

| Вызов | Что кладёт в очередь |
|-------|----------------------|
| `post(Runnable)` | `Message` с `callback = r`, `when = now` |
| `postDelayed(r, ms)` | то же, `when = now + ms` |
| `postAtTime(r, uptime)` | `when = uptime` (абсолютный момент) |
| `postAtFrontOfQueue(r)` | `when = 0` — в начало очереди |
| `sendMessage(msg)` / `sendMessageDelayed` | `Message` с `what`/`arg1`/`obj`, обрабатывает `handleMessage` |

`Runnable` vs `Message`: `Runnable` несёт код прямо в себе (`callback`); `Message` несёт данные
(`what`, `obj`), а логику держит `handler.handleMessage`. Внутри — один и тот же механизм. Каждый
`Message` **переиспользуется** из пула (`Message.obtain()` / `recycle()`) — не создавай `new Message()`
вручную в горячем коде.

## 6. Отмена: `removeCallbacks` и токены

Отложенное сообщение можно снять, **пока оно ещё в очереди**:

```kotlin
handler.postDelayed(task, 1000)
handler.removeCallbacks(task)                 // по ссылке на Runnable
handler.sendMessageDelayed(msg /*what=1*/, …)
handler.removeMessages(1)                      // по what
handler.removeCallbacksAndMessages(token)      // всё с данным token разом
```

**Токен** — произвольный объект-ярлык (`Handler` кладёт его в `Message.obj` при `postDelayed(r, token, …)`),
чтобы одним вызовом снять пачку связанных сообщений (например, при уничтожении экрана).
Снять **уже выполняющееся** сообщение нельзя — только то, что ещё ждёт в очереди. → задачи **Л6, Л7, С11**.

## 7. Sync-барьеры и асинхронные сообщения

`MessageQueue.postSyncBarrier()` вставляет специальный **барьер** (сообщение без `target`). Пока он
стоит, `next()` **пропускает все синхронные** сообщения и отдаёт только **асинхронные**
(`Message.setAsynchronous(true)`), даже если синхронные стоят раньше по времени.

Зачем: система ставит барьер на время подготовки кадра и помечает **ввод и `Choreographer`-коллбэки
как async** — чтобы отрисовка следующего vsync не тормозилась пользовательскими сообщениями в
очереди. Когда кадр отрисован — барьер снимается (`removeSyncBarrier`), синхронные снова текут.
→ задачи **С12, СЛ17**.

Практический след: `Handler(looper, /*async=*/ true)` или сообщения с `setAsynchronous(true)`
«проскакивают» барьер. Обычному коду это почти никогда не нужно — но на собеседовании про это спрашивают.

## 8. `IdleHandler`: работа «на простое»

`MessageQueue.addIdleHandler { … }` регистрирует коллбэк, который зовётся, когда очередь **опустела**
(делать прямо сейчас нечего). Контракт `queueIdle()`:
- вернул `true` → остаться зарегистрированным (позовут в следующий idle);
- вернул `false` → снять себя после этого вызова.

Идея — отложить **низкоприоритетную** работу (прогрев кэша, аналитика, дострой не-видимых `View`)
на момент, когда поток свободен, не воруя время у кадров. `Looper.getMainLooper().queue.addIdleHandler`
— основа таких приёмов, как отложенная инициализация. → задачи **С15, СЛ19**.

## 9. Один поток — один в моменте: корень jank и ANR

Цикл **однопоточный**: пока выполняется одно сообщение, все остальные ждут, даже если их `when`
давно наступил (**head-of-line blocking**). Отсюда:

- **Jank (пропуск кадров).** Система шлёт на главный поток vsync-сигнал каждые ~16.6 мс (60 Гц). Если
  сообщение (например, тяжёлый `onBindViewHolder` или парсинг JSON на UI) держит поток дольше — кадр
  не успевает отрисоваться, пользователь видит рывок. → задачи **СЛ16, СЛ20**.
- **ANR (Application Not Responding).** Если главный поток не обработал сообщение доставки ввода за
  ~5 с (или `BroadcastReceiver` за ~10 с, и т.д.), система показывает диалог «приложение не отвечает».
  ANR — это **буквально** «цикл событий застрял на одном сообщении слишком долго» (или дедлок, или
  сообщение так и не дошло до головы из-за более раннего долгого).

Отсюда золотое правило: **никакой блокирующей работы на главном потоке** (сеть, диск, тяжёлый CPU) —
её выносят на фоновые потоки/пулы/корутины, а результат возвращают на главный через `Handler`/`post`.

### fixed-delay vs fixed-rate у повторяющихся задач

Повторяющийся `Runnable` обычно перепланирует себя в конце (`handler.postDelayed(this, interval)`).
Если работа занимает `work` мс, период «плывёт» на это время (**fixed-delay**): реальные старты идут
через `work + interval`. Если нужен ровный ритм по сетке (**fixed-rate**, как у `Choreographer` по
vsync) — следующий старт считают от `i * interval`, а не от финиша, и планировщик «догоняет»
расписание, когда отстал. → задача **СЛ18**.

## 10. `HandlerThread`: свой цикл на фоновом потоке

`Looper` бывает не только у главного потока. `HandlerThread` — готовый рабочий поток со своим
`Looper`, чтобы **сериализовать** задачи на одном фоновом потоке (например, обращения к `Camera`,
`SQLite`, к железу — всё с одного потока = никаких гонок, thread confinement):

```kotlin
val ht = HandlerThread("io").apply { start() }
val bg = Handler(ht.looper)
bg.post { /* всегда на потоке "io" */ }
// завершение:
ht.quitSafely()   // доработать уже готовые сообщения и остановить цикл
// ht.quit()       // остановить немедленно, бросив всю очередь
```

- **Confinement.** Все сообщения одного `Handler` идут на его единственный поток по одному — это даёт
  бесплатную сериализацию доступа к состоянию (не нужны локи). → задача **С14**.
- **`quit()` vs `quitSafely()`.** `quit()` роняет очередь немедленно; `quitSafely()` доставляет уже
  **готовые** (`when <= now`) сообщения, отбрасывает отложенные в будущее, затем останавливает цикл.
  → задача **С13**.
- **Не забыть завершить** `HandlerThread` — иначе поток живёт вечно (утечка потока).

`HandlerThread` — это тема 2 модуля; здесь достаточно понимать, что цикл событий — не привилегия
только главного потока.

## 11. Почему `Handler`/анонимные `Runnable` текут (Android-классика)

Нестатический внутренний класс (в т.ч. анонимный `Runnable`/`Handler`) держит **неявную ссылку на
внешний объект** (`this$0`). Если отложенное сообщение живёт в очереди дольше, чем `Activity`
(например, `postDelayed(r, 60_000)`), то `MessageQueue` → `Message` → `Runnable` → `Activity`
удерживает уничтоженную `Activity` в памяти → утечка. Лечение: статический `Handler` +
`WeakReference`, либо снимать сообщения в `onDestroy` (`handler.removeCallbacksAndMessages(null)`).
Подробно — тема «Потоки и жизненный цикл» этого модуля и [`handbook.java.memory`](../../java/memory/THEORY.md).
